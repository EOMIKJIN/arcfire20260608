## 0. 한 줄 요약

**대표님 1명의 기록을 「0번 플레이어」로 삼아 처음부터 10만 명과 같은 스키마로 수집한다.** 기기에서 요약하고(원문 이벤트는 기기 밖으로 안 나감) 하루 1번만 올리며, 플레이봇은 「봇 자기 결과」가 아니라 **사람 데이터에서 뽑은 행동 분포**를 따라 배우고, 사람 분포에서 얼마나 벗어났는지로 평가받는다.

```text
① 원시데이터            ② 봇 학습                       ③ 인간 근접 자가플레이
대표님(n=1) ─┐
테스터(n≈100) ┼─ 같은 스키마 ─► 행동분포 팩 ─► 봇 모방 ─► 자가플레이 ─► 사람 분포와 거리 평가
유저(n→10만) ─┘   (일 1회)      (야간 Node)     (전이표)    (트윈 보정)     (통과분만 채택)
```

## 1. 설계 원칙 (규모가 커져도 바뀌지 않는 것)

| # | 원칙 | 이유 |
|---|------|------|
| 1 | **스키마는 1명일 때 확정, 10만 명일 때도 동일** | 대표님 데이터가 미래 데이터와 그대로 비교·합산돼야 함 |
| 2 | **기기에서 요약, 원문 이벤트 업로드 금지** | 비용·개인정보·메모리 모두 이 한 줄로 통제 |

## 2. 데이터 계층 (기기 → 클라우드 → 봇)

| 층 | 무엇 | 어디 | 크기·빈도 |
|----|------|------|-----------|
| **L0 사건** | `{tSec, verb, ctx}` 예: `land arcadia_prime`, `scan`, `mine_granted`, `trade_sell`, `quest_accept story_001`, `combat_start/end(win/lose)`, `hop A→B`, `hold`, `app_bg` | **기기 메모리 고정 링버퍼 256칸** | 디스크 쓰기 없음 |
| **L1 세션 요약** | 순서 해시·동사별 체류초·첫 퀘 수락 시각·패배 후 행동·튜토리얼 준수율·이탈 지점 | 세션 종료(백그라운드 전환) 시 AsyncStorage **1회** | ≤4KB, 최근 32세션 캡 |
| **L2 일일 다이제스트** | 하루 세션 합산: 동사 전이 횟수표(n-gram 상위)·체류 분포 버킷·도달한 진행 단계·전투 승패/레벨차 | 기존 RTDB `learning/devices/{uid}/…` 경로 **1 write/day** | ≈2KB |
| **L3 인간 행동 팩** | 전체 집계: 전이확률표·체류 분위수·단계별 도달률(퍼널)·플레이 성향 군집 | Node 야간 배치 → **git** (`HumanPatternPack`) | 수백 KB, 일 1회 |
| **L4 봇 정책** | 팩에서 유도한 봇 행동 모델 + 트윈 보정값 | `tools/play-bot-console/learned/` | 승인 후 교체 |

- L0 동사 목록은 v1 설계문서 §4-1 `SessionTrace` verbs를 그대로 쓴다(스키마 통일).
- 순서 정보는 원문 시퀀스가 아니라 **「A 다음 B」 전이 횟수표**로만 올린다 → 크기 고정·재식별 위험 감소.

## 3. 단계별 계획 (규모에 따라)

### 단계 A — 지금, n=1 (대표님)

| 항목 | 내용 | 앱 변경 |
|------|------|---------|
| A-1 | DEV 빌드 logcat의 기존 마커(`[MEM_PROFILE] stage/event` — 허브 진입 행성·지도 hop A→B·지도 복귀 등)를 PC에서 수집 → **SessionTrace v0** 변환 스크립트 | **없음** |
| A-2 | 허브 동사(스캔·채굴 지급·무역·퀘 수락/목표·전투 시작/종료) **DEV 한정 로그 1줄씩** 추가 | 소 (승인 필요) |
| A-3 | 대표님 세션으로 **「대표님 페르소나」** 생성 — 하드코드 페르소나 가중 대체 | 없음 (Node) |
| A-4 | 트윈 상수 보정: 전투 승률(레벨차별)·무역 빈도·체류 시간을 대표님 실측값으로 | 없음 (Node) |
| A-5 | 1차 목표: **봇이 대표님 세션 순서를 재현** (모방 기준선) | — |

> n=1은 「평균적인 사람」이 아니라 **기준 플레이어 1명**이다. 이 단계 목표는 일반화가 아니라 스키마·파이프라인을 실데이터로 검증하는 것.

### 단계 B — 테스터, n≈10~100

- 앱 내 L0 링버퍼 + L1 세션 요약 + L2 일일 다이제스트 업로드(옵트인 토글).
- **스키마 v1 동결**, 앱/밸런스 버전 태그, 계정 초기화 purge 연동, 동의 문구.
- 대표님 데이터(L1)와 테스터 데이터를 같은 집계에 합류 → 첫 「인간 분포」.

### 단계 C — 소프트런칭, n≈1,000~10,000

- 모든 기기는 L2 다이제스트만, **상세 세션 요약(L1)은 표본 5%만** 업로드.
- 성향 군집(예: 스토리형·전투형·무역형·이탈형)을 데이터로 추출 → **봇 페르소나 = 실제 군집**.
- 버전 코호트 분리: 밸런스 변경 전후를 따로 집계.

### 단계 D — 10만 명

- 업로드는 그대로 1회/일·≈2KB. 서버 측은 **원본 다이제스트 7일 보관 → 야간 집계 후 삭제**, 집계 결과만 장기 보관.
- 군집·분포가 안정되면 봇 학습을 **주 1회 재학습 + 매일 평가**로 운영.

## 4. 플레이봇 학습 방식의 진화

| 단계 | 봇이 배우는 방식 | 지금과의 차이 |
|------|------------------|---------------|
| 1 모방 | 인간 팩의 **상황별 전이확률표**(지금 화면·레벨대·자금 상태 → 다음 동사)를 그대로 샘플링 | 하드코드 `decideIntentKind` 규칙과 12% 가중 대신 데이터가 행동을 결정 |
| 2 보정 | 트윈 상수(승률·보상·국경 확률)를 실측 분포에 맞춤 | 트윈이 지어낸 역학 제거 |
| 3 자가플레이 | 모방 정책에서 출발해 정체·반복을 줄이는 방향으로 탐색. 단 **사람 분포에서 너무 멀어지면 벌점** | 지금처럼 같은 방향으로 무한히 밀리는 고착 불가 |
| 4 평가·채택 | 새 정책은 아래 지표로 **현재 정책보다 사람에 가까울 때만 채택**, 아니면 롤백 | 지금은 평가 없이 매 5초 덮어씀 |

**인간 근접 평가 지표** (봇 vs 최신 인간 코호트, 학습에 안 쓴 검증용 데이터로):

- 전이확률표 거리(분포 차이) · 세션 순서 상위 N개 교집합(orderJaccard, v1 문서 §4-2)
- 단계별 도달률(퍼널) 곡선 차이 · 체류 시간 분위수 차이
- 패배 후 행동 분포(수리/이동/재도전) 차이

## 5. 비용·한계 (10만 명 기준 · 확인 필요)

| 항목 | 추정 | 메모 |
|------|------|------|

| 대응 1 | 단계 C처럼 **표본 업로드**(예 5% = 5천 명 × 2KB = 10MB/일) | 무료 한도 내 운영 가능성 |
| 대응 2 | 보관 7일 후 집계·삭제 | 저장량 상한 고정 |
| 대응 3 | 유료 전환 여부 | **대표님 결정 사항** (현재 「종량 $0」 원칙과 충돌) |

```text

```

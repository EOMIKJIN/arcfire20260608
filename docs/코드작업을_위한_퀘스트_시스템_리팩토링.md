## 0. 한 줄 결론

효율 병목의 1순위는 **활성 목록 인덱스**가 아니다. 주간 보드가 `arc_inst_*` id를 재사용하면서 **이미 완료한 진행과 충돌**하고, 완료 전이와 보상 저장이 **원자적이지 않다**. 이 두 가지를 고치지 않은 채 persist를 늦추면 수락 불능과 보상 이중 지급이 커진다.

게임 규칙(트랙, 바 보드 상한, 메인 스토리 `ready`만 수락, 입≠몸, 목표 boolean)은 유지한다.

```text
[pss-pre-dev] hot_path=주간 보드 갱신(일일 배치) · finalize 1회 alloc=완료 진행 정리 O(cleared) cache=진행키=instanceId
[pss-pre-dev] stage=계정 영속(STAGE dispose 대상 아님) risk=P6 완료/보상 분리 쓰기 · A1 미정리 시 blob 증가
[pss-pre-dev] verdict=REDESIGN — 0단계(id 충돌 정리·완료 원자화) 승인 전 구현 보류
```

### 김팀장 판정 (김클로드 재검수)

| # | 김클로드 | 김팀장 |
|---|---|---|
| 활성 id 인덱스·타입 버킷 | N=3000 순회 0.05ms, 이득 없음 | **보류**. 1차 착수에서 빼다 |
| persist 이중 쓰기 | 정상 이벤트는 1회, 만료 시에만 2회 | **동의**. sweep+완료 flush 합치기는 만료 경로만 |

| 앱 사망 시 대사 미복구 | 하이드레이트가 active·전목표완료를 복구 | **동의**. 진짜 위험은 **보상 재지급** |

## 2. 현재 구조 (재조사)

진행은 다섯 출처가 **진행 스토어 하나**로 모인다. 카탈로그 조회는 세 겹이다.

```text
수락 출처
  missions.csv          mission_* 튜토리얼 · story_* 본편 · sandbox_* / tq_* 템플릿
  바 보드 클론           arc_inst_*     (템플릿을 행성 보드에 materialize)
  함장 개인              cp_* → arc_cpt_* (통신 1회 0~1, 바 보드와 Map 분리)

조회 getMissionById
  1. 인스턴스 materialize Map
  2. 함장 개인 materialize Map
  3. MISSIONS_FROM_CSV

진행 저장 arcfire_missions_v1
  { progresses, activeMissionId } 만 기록
  완료·만료·활성 이 한 객체
  대기 중 클리어 대사 큐는 메모리만. 하이드레이트는 active·전목표완료면 대사를 다시 만든다

그 밖 계정 키 (진행 blob 과 분리, 유지)
  arcfire_arc_core_instance_missions_v1   바 보드
  arcfire_main_story_progress_v1          선택지·챕터 종료 씬
  arcfire_main_story_captain_dead_v1      함장 사망
```

목표 타입은 `reach_system` · `reach_planet` · `defeat_enemy` · `deliver_cargo` · `buy_goods` · `talk_npc`.  
스토어 완료 칸은 **목표 id → boolean** (`MissionProgress.objectives`). `completeObjective` 는 그 칸을 `true` 로만 바꾼다. `src/engine/MissionEngine.ts` 는 이 경로에 연결되어 있지 않다.

`buy_goods` 만 완료 **전**에 `quantity`(없으면 1)와 인벤 수량을 비교한다. 충족하면 boolean 한 칸이다. `defeat_enemy` 의 `quantity` 는 v1 에서 쓰지 않는다(1체, 베뉴+템플릿 일치). `deliver_cargo` 는 DSL 에 의미만 있고, 인도 UI 가 `completeObjective` 를 호출하는 연결은 없다. objectives 91행 실측: reach_system 30 · buy_goods 27 · defeat_enemy 25 · reach_planet 6 · talk_npc 3 · deliver_cargo 0.

### 2-1. 이벤트 적용 지점

착륙·구매·대화·HUD·배치·함장 핀은 `listActiveMissionBundles(progresses)` 를 호출한다. 함수는 `status !== 'active'` 를 건너뛴다. 완료 키는 한 바퀴 돈다. 격파는 `questCombatLock` 이 활성 미완료 `defeat_enemy` 1건만 본다.

| 이벤트 | 모듈 |
|---|---|
| 착륙 (`reach_planet` · 허브 착륙 `reach_system`) | `applyLandedMissionObjectives.ts` · `missionPlanetHubSync.ts` |
| 성계 도달 | `applyReachSystemMissionObjectives.ts` — 완료 게이트는 `hub_landing` 만 |
| 구매 (`buy_goods`) | `applyBuyGoodsMissionObjectives.ts` |
| 대화 (`talk_npc`) | `talkNpcObjective.ts` → `applyTalkNpcMissionObjectives.ts` |
| 격파 (`defeat_enemy`) | `applyDefeatEnemyMissionObjectives.ts`. 호출은 `PlanetEdenRaidTestLayer.tsx` |
| HUD 슬롯 | `missionHudSlots.ts` — 정렬 tutorial > main_story > quest |
| 퀘스트 배치 스캔 | `questItemOpsRegistry.ts` |
| 허브 함장 핀 | `planetHubPinnedInfoCaptains.ts` |

`persistMissions` (`missionStore.ts`) 는 매 호출마다 `progresses` 전체 + `activeMissionId` 를 `JSON.stringify` 하고 `AsyncStorage.setItem` 한 뒤 `scheduleUserCloudSync()` 를 건다.  
클라우드는 **이미** 900ms 디바운스 + 최소 120초 간격이다. 120초 안에 타이머가 울리면 **재예약 없이 return** 하므로, 그 사이 변경은 다음 `scheduleUserCloudSync` 또는 30분 백업까지 올라가지 않을 수 있다.

### 2-2. 두 materialize Map 은 합치지 않는다

| Map | 파일 | 이유 |

| 함장 개인 | `captainPersonalMissionResolver.ts` | 통신 1회. 틱에서 전량 rebuild 금지 |

## 5. 리팩터 설계 (개정)

### 5-0. 0단계 — 정확성 (기본 착수)

플레이어가 보는 보상 액수·보드 칸 수·목표 boolean은 그대로 둔다.

#### A1 [P0] 주간 갱신 id 재사용

`refreshArcCoreInstanceMissionBoardState` 는 `accepted` 만 남긴다. id는 `arc_inst_<행성>_<seq 2자리>` 이고, 발급은 **현재 보드에 남은 id만** 피한다. 완료 진행은 만료가 아니면 지우지 않는다. 진행 키 = instanceId. 재발급 후 수락은 `already_complete`, 목록은 `completed`.

**채택 (a) — 정리 + 발급 회피. (b) 사이클 번호를 id에 넣는 것은 본선이 아니다.** (b)만 하면 진행이 무한히 는다.

0단계에서 함께 할 일:

1. 주간 갱신(및 동일 함수를 쓰는 경로) 직후, 보드에 더 이상 없는 `arc_inst_*` 의 `complete`/`failed` 진행을 미션 스토어에서 제거한다. `accepted`·`listed`·활성은 건드리지 않는다.
2. `allocateUniqueArcCoreInstanceId` 는 보드 id **와** 남은 진행 키를 함께 피한다.
3. 제거한 건수만큼 **계정 귀속 완료 카운터**만 더한다 (`clearedArcInstCount` 등, 숫자 1개). 제목 스냅샷은 최근 N건(상한 32)만. 무제한 이력 배열 금지.
4. 튜토리얼·메인 스토리·`sandbox_*` 정적 id 완료는 지우지 않는다.

#### A2 [P1] 완료 전이 원자화

`finalizeMissionCompletion` 과 대사 없이 바로 끝나는 완료:

1. 메모리에서 `status:'complete'` + `rewardedAt` 표시.
2. **미션 blob을 먼저 `await persistMissionsImmediate()`**.
3. 그 다음 보상. 보상이 다시 들어와도 `rewardedAt` 이 있으면 지급하지 않는다.
4. 목표 boolean·수락만 코얼레스 대상. 완료 전이는 코얼레스하지 않는다.

#### A3 [P2] 만료 화물 회수

`quantity` 가 없거나 0이면 `MAX_SAFE_INTEGER` 가 아니라 **1**. 그 미션이 준 화물과 무역 보유분을 구분하는 원장은 이 단계에서 만들지 않는다(기존값·스키마).

#### A4 클라우드 드롭

120초 창에서 타이머가 버려지면 **한 번 더 예약**한다. 고빈도 틱에서 클라우드를 직접 쏘지 않는다. 완료 전이 직후는 로컬 미션 persist가 우선이고, 클라우드는 기존 스케줄 + 재예약만 고친다.

### 5-1. 1단계 — persist 규율 (0단계 이후)

1. **수락·목표 boolean만** 1.5초 코얼레스. 미션 전용 타이머 1개. 플레이어 지갑 타이머와 공유하지 않는다.
2. **reset / purge = cancel**. flush 후 `removeItem` 금지.
3. **AppState `background`/`inactive` 전역 1회** (`app/_layout.tsx`). 대기 중인 미션 persist만 flush. 화면마다 리스너를 늘리지 않는다. `setInterval` 금지.
4. 만료 sweep 과 목표 완료가 한 이벤트면 stringify 1회.

활성 id 목록·타입 버킷은 **이 단계에 넣지 않는다**.

### 5-2. 2단계 — 저장 형식·클라우드 요약 (0단계 후 재판정)

A1 정리 뒤 진행 수가 행성×16 근처로 묶이면 형식 분리는 **하지 않는다**.  
정리 뒤에도 완료 정적 미션+개인 미션이 커지거나 클라우드 문서가 1MiB에 가까우면, 그때 활성 전량 + 완료 최근 N 만 올리도록 캡을 검토한다. 구 키 이행은 대표님 승인 후.

### 5-3. 하지 않는 것

| 항목 | 이유 |
|---|---|
| 활성 인덱스·타입 버킷 (1차) | 실측 이득 없음. 복잡도만 증가 |

## 6. 코드 작업 순서

대표님이 **0단계 착수**를 지시한 뒤에만 연다.

| 순서 | 파일 | 변경 |
|---|---|---|
| 0a | `arcCoreInstanceMissionGenerator.ts` · `missionStore.ts` | 갱신 후 고아 `arc_inst_*` complete/failed 제거 + 카운터 |
| 0b | `arcCoreInstanceMissionIds.ts` | 발급 시 보드+진행 키 회피 |
| 0c | `missionStore.ts` | `rewardedAt` · 완료는 즉시 persist 후 보상 |
| 0d | `missionTimeLimit.ts` | 회수 quantity 폴백 1 |
| 0e | `userCloudSyncSchedule.ts` | 120초 창에서 드롭 시 1회 재예약 |
| 1a | `missionStore.ts` | boolean/수락 코얼레스 · reset cancel |
| 1b | `app/_layout.tsx` | AppState background 미션 flush 1회 |

게이트:

- `npx tsc --noEmit -p tsconfig.client.json`
- 주간 갱신 후 재발급 id 가 이전 완료와 충돌하지 않음 (순수 함수 + 가능하면 스토어)
- 완료 직후 강제 종료 → 재실행 시 보상 1회
- 계정 초기화 후 `arcfire_missions_v1` 없음 (타이머가 키를 다시 만들지 않음)
- 수락 → 착륙/구매/대화 완료 → 재실행 후 진행 유지
- 만료 sweep 후 보드 listed 복귀
- 완료 판정·보상 **수치**가 리팩터 전과 같음

## 7. 코드 전 승인 항목

0단계(A1 정리·A2 원자화)는 완료 조건과 보상 액수를 바꾸지 않는다. 주간 갱신 뒤 **새 의뢰가 다시 수락**되는 것이 보이는 변화다.  
수량 목표·반복 퀘스트·포기 UI는 이 문서의 착수 범위가 아니다.

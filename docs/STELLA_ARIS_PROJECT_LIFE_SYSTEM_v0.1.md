## 0. 한 줄 판정

**대표님 의도는 현재 구조에서 구현 가능하다. 단, 「주기적으로 도는 틱」을 만들면 실패한다.**

라이프는 **타이머로 돌리지 않고, 시계에서 읽어 낸다.** 계산은 플레이어가 대화를 열 때 1회, 정산은 기존 일 1회 배치에 얹는다. 이것이 폰 부하·배터리·Android 백그라운드 제약·헌법 §금지4를 동시에 푸는 유일한 경로다.

| 대표님 의도 | 판정 | 한 줄 |
|------|------|--------|
| 하루 일상을 그대로 행동 | **가능** | 결정론적 가상 시계 + 라이프 패턴 CSV. 48슬롯/일 |
| 학습하고 저장하고 기억 | **가능** | 3계층(세션·일일·고도화). 원본은 버리고 고도화본만 남김 |
| 과도한 데이터 금지 | **가능** | 총 **≤3KB** 고정 예산. 상한 단언 테스트로 잠금 |
| 최대 저장일 + 전체 교체 업데이트 | **가능** | L1 14일 → 초과분을 L2에 EMA 흡수 후 **원본 폐기** |
| 주기 10분/30분/1시간 | **조건부** | **틱이 아니라 슬롯 해상도**로 해석. 권장 **30분**. CPU 주기 실행 0 |
| 플레이어 대화가 영향 요소 | **가능** | anchors(≤6) + mood 델타. 신규 관측 0 |
| 게임 안 실제 행동기반에 사용 | **부분** | **스텔라의 발화 행동**에 사용. 월드 write는 입≠몸으로 계속 금지 (§3-6) |
| LLM + 기존 템플릿과 이어지는 사고수준 | **가능** | 라이프는 100% 로컬 생성 → 팩 재료로만 투입. 턴당 LLM **1홉 유지·추가 0** |
| 동기·목표 등 최소 사고 변수 | **가능** | 스칼라 **7개**(§4-3). 슬라이더·친밀도 게이지 아님 |
| 별도 서버 없이 Firebase/서버리스 | **가능** | 로컬 AsyncStorage가 정본. Firestore 신규 컬렉션 **0**, 기존 세이브 사이클 편승 |

**이번 설계에서 열지 않는 것**: 라이프 전용 타이머·백그라운드 잡 · 라이프 LLM 호출 · ObservationBus publish · 친밀도 단계 FSM · 월드 write · 신규 오버레이/STAGE.

## 1. 기획 의도 분석 — 지시를 6개 요구로 분해

대표님 문장을 설계 단위로 쪼개면 아래 6개다. 각각 **무엇이 진짜 요구이고, 무엇이 구현 수단인지** 갈라야 충돌이 풀린다.

| # | 대표님 문장 | 진짜 요구 (목적) | 대표님이 제시한 수단 | 설계 판단 |
|---|---|---|---|---|
| R1 | 하루의 일상을 그대로 행동 | 스텔라에게 **대화 밖의 시간**이 있어야 한다 | — | 채택. 수단은 자유 |
| R2 | 학습·저장·기억 | 어제와 오늘이 **이어져야** 한다 | — | 채택 |
| R3 | 10분/30분/1시간 주기 작동 | 시간이 흐르면 **상태가 변해야** 한다 | 주기 실행 | **수단 교체** — 지연 평가(§3-1) |
| R4 | 과도한 데이터 금지·최대 저장일·전체 교체 | 무한 성장 **금지** | 보존일 + 합본 | 채택. 그대로 구현 |
| R5 | 질문·생각·대답 3요소로 표현 | 라이프가 **대화에서 보여야** 한다 | 3요소 | 채택 (§6) |
| R6 | 동기·목표 등 최소 변수 | 행동에 **이유**가 있어야 한다 | 수치 변수 | 채택. 7개로 제한 |

**R3이 이번 설계의 분기점이다.** 「주기적으로 작동」의 목적은 *상태가 시간에 따라 변하는 것*이지 *CPU가 주기적으로 도는 것*이 아니다. 후자를 문자 그대로 구현하면 `setInterval` 하나가 다음을 동시에 위반한다.

- CLAUDE.md 절대금지 4 — 고빈도 실행
- PSS §0-A — 틱 할당
- Android 백그라운드 — 앱이 내려가면 JS 타이머는 **어차피 안 돈다** (즉 기능도 실패)
- 배터리·발열 — 1인 테스트기에서 즉시 체감

전자는 순수 함수 1개로 끝난다. **결과는 같고 비용은 0이다.**

## 3. 근본 설계 결정 6개

이 6개가 문서의 골자다. 나머지는 파생이다.

### 3-1. D1 — 틱을 만들지 않는다. 시계에서 읽는다 (핵심)

```text
[기각] setInterval(10분) → 상태 갱신 → persist
        · 백그라운드에서 안 돎 (기능 실패)
        · 돌면 PSS·배터리·헌법 위반

[채택] resolveStellaLifeAt(nowMs) : 순수 함수
        · 호출 시점의 시계로 "지금 무엇을 하고 있는지"를 계산
        · 타이머 0 · 백그라운드 의존 0 · 할당 스칼라 7개
```

**계산 규칙** (결정론):

```text
dayKey    = KST 기준 yyyyMMdd
slotIndex = floor(KST 자정 이후 분 / SLOT_MIN)        // SLOT_MIN=30 → 0..47
seed      = hash32(uid, dayKey, slotIndex)
activity  = 라이프패턴CSV[슬롯대역] 후보 중 seed로 1개
```

같은 입력 → 항상 같은 출력. 서버 왕복 없음. 저장 없음(L0).

**왜 이것이 「주기적으로 작동」을 충족하는가**: 플레이어가 09:00에 열면 「아침 브리핑 정리 중」, 14:00에 열면 「항로 데이터 검수 중」, 23:00에 열면 「당직 교대 직전」이 나온다. **상태는 실제로 30분마다 변한다.** 변하지 않는 것은 CPU 사용량뿐이다.

**슬롯 해상도 권장 = 30분**

| 해상도 | 슬롯/일 | 평가 |
|---|---|---|
| 10분 | 144 | 해상도 과잉. CSV 대역·문장이 144칸을 못 채우면 반복 체감. 이득 없음 |
| **30분** | **48** | **권장.** 하루를 자연스럽게 나누고, 하루 여러 번 열어도 매번 다른 장면 |
| 60분 | 24 | 하루가 단조. 오전/오후가 한 문장으로 뭉침 |

해상도는 **CSV 상수 1개**다. 실기 후 대표님 판단으로 바꿀 수 있고, 코드 구조는 그대로다.

### 3-2. D2 — 라이프 생성은 100% 로컬 결정론. LLM 홉 추가 0

라이프 문장을 LLM이 만들면 하루 48슬롯 × 유저수 = 무료 티어 쿼터가 즉시 붕괴하고 ZERO_BILL이 깨진다.

```text
라이프 생성   = 로컬 CSV + seed        (비용 0 · 오프라인 동작)
라이프 사용   = 팩에 문자열로 실림      (기존 턴당 1홉 안에서)
```

LLM은 라이프를 **만들지 않고, 받은 재료로 말한다.** 이 분리로:

- 무료 티어 쿼터 영향 **0**
- 오프라인·429에도 라이프 **정상 작동** (G3 폴백도 같은 문장 사용)
- 라이프 문장의 세계관 정합성을 CSV에서 **검수 가능** (모델 환각 없음)

### 3-3. D3 — 3계층 기억 + 고도화 교체

대표님 요구 R4의 직역이다.

```text
L0 세션 휘발   지금 슬롯·직전 8턴        persist 없음        메모리만
L1 일일 다이제스트  하루 1행 · 최대 14일   ≤1.7KB            원본
L2 고도화 코어     고정 크기 · 무기한     ≤1.2KB            합본
                    ↑
        일 1회 배치: L1 15일째 → L2에 EMA 흡수 → L1에서 삭제(원본 폐기)
```

**무한 성장이 구조적으로 불가능하다.** L1은 링버퍼 14칸, L2는 고정 필드. 총 예산 **≤3KB**를 테스트로 단언한다.

### 3-4. D4 — Learning 축과 단방향

`ARC_CORE_SUSTAINABLE_LEARNING_MODEL_v1.md`의 축(ObservationBus → LearningStore → PolicyPack)은 **경제·전투 학습**이고, `arcCoreChatJudgmentMemory.ts` 주석이 「ObservationBus·learning-state·Policy Pack과 공유 금지」로 이미 잠갔다.

```text
Learning 축  ──(읽기 전용 스칼라 ≤5)──▶  스텔라 라이프
스텔라 라이프 ──────── publish 금지 ────X──▶  Learning 축
```

라이프는 일일 배치가 **이미 만들어 둔 결과 스칼라**(오늘 배치 성공 여부, 행성 코어 등급 등)만 소비한다. 신규 관측·신규 버스·신규 flush **없음**.

### 3-5. D5 — 친밀도가 아니라 공유 맥락

김팀장 HOLD(§2-3) 존중. **수치화된 호감도·단계·해금을 만들지 않는다.**

| 만들지 않음 | 대신 |
|---|---|
| `affection` / `intimacy` 0~100 | 없음 |
| 4단계 FSM + 단계별 해금 | 없음 |
| 대화 횟수 보상 | 없음 |
| 거절 시 톤 페널티 | 없음 |
| — | `anchors` ≤6 — 플레이어가 말한 **사실의 기억** (이름·선호·약속) |
| — | `sharedDays` — 같이 보낸 날 수 (표시용 정수, 게이트 아님) |

차이가 중요하다. **기억은 인격이고, 게이지는 공략이다.** 이 설계는 기억만 만든다.

### 3-6. D6 — 「실제 행동기반」의 정확한 범위

대표님 문장 중 **가장 조심해야 할 부분**이라 먼저 밝힌다. 「게임 안의 실제 행동기반에 사용」은 두 가지로 읽힌다.

| 해석 | 판정 | 이유 |
|---|---|---|
| (a) 스텔라의 **발화·선제 대화·화제 선택**이 라이프에 따라 달라진다 | **채택 · 본선** | 입의 일이다. 충돌 없음 |
| (b) 라이프가 **월드를 바꾼다** (크레딧·언락·배치·점유) | **기각** | 입≠몸 — 3개 정본이 동시에 금지 |
| (c) 라이프가 **제안 id 선택에 편향**을 준다 | **예약만** | `ARC_CORE_CHAT_WORLD_PROPOSAL_LIVE=false`. B 열릴 때 재검토 |

(a)만으로도 체감은 충분하다. 스텔라가 「어제 그 항로 얘기 계속 신경 쓰였어」라고 **먼저** 말하면, 플레이어에게는 그것이 「실제로 살고 있는 것」으로 읽힌다. 월드 write는 필요 없다.

이 범위 조정이 대표님 의도를 축소한다고 판단되시면, (c)를 여는 것이 다음 단계다 — 다만 그것은 B 스위치 결정이지 라이프 설계 결정이 아니다.

## 4. 라이프 시뮬레이션 모델

### 4-1. 하루의 구조 (20~30대 여성 · 고도화 오퍼레이터 · 아크파이어 우주)

직업 설정은 이미 정본에 있다 — 스텔라는 **스텔리움 연합에 본체를 둔 파생 입**이고, 플레이어에게 정보·안내를 준다(`op_persona_office`). 일상은 그 직업 위에 얹는다.

| 대역 (KST) | 슬롯 | 직무 축 | 개인 축 |
|---|---|---|---|
| 06:00–09:00 | 12–17 | 야간 항로 로그 인수·브리핑 정리 | 기상·커피 대신 뭘 마실지(이미 persona 9행) |
| 09:00–12:00 | 18–23 | 관측 데이터 검수·연합 통신 | 집중 구간 |
| 12:00–14:00 | 24–27 | 일일 운용 결과 확인 (배치 시각과 정합) | 식사·짧은 휴식 |
| 14:00–18:00 | 28–35 | 항로 이상 추적·보고서 | 소소한 잡무 |
| 18:00–22:00 | 36–43 | 당직 인계·경보 모니터 | 사적 시간·취향 |
| 22:00–02:00 | 44–47, 0–3 | 야간 당직 또는 비번 | 야식·정리·독서 |
| 02:00–06:00 | 4–11 | 수면 (비번일 때) | — |

**요일 축**: `dayOfWeek`로 비번/당직 교대를 만든다. 같은 화요일이라도 주차가 다르면 seed가 다르다.

수면 슬롯에 플레이어가 말을 걸면? — 스텔라는 파생 입이므로 **항상 응답 가능**하되, 「자고 있었다」가 아니라 「비번이라 좀 늘어져 있었어」 같은 톤이 된다. 응답 거부는 만들지 않는다(안내원 기능을 해침).

### 4-2. Table-First — 신규 CSV 3장

기존 밸런스·대화 CSV는 **불변**. 신규 3장만 추가하고 `build:content-tables`로 generated Map을 만든다. 런타임 `find` 금지.

| 테이블 | 역할 | 주요 컬럼 |
|---|---|---|
| `tables/content/stella_life_slots.csv` | 슬롯 대역별 활동 후보 | `id, slot_from, slot_to, weekday_mask, duty_or_off, activity_ko, activity_en, energy_delta, focus_delta, topic_hint` |
| `tables/content/stella_life_goals.csv` | 목표·동기 카탈로그 | `id, drive_id, goal_ko, goal_en, span_days, progress_step, retire_rule` |
| `tables/content/stella_life_env_rules.csv` | 환경 변수 → 변수 델타 | `id, env_key, condition, mood_delta, focus_delta, line_ko, line_en` |

문장은 전부 CSV. 코드 하드코딩 **금지**(기존 계약 동일).

### 4-3. 사고 최소 변수 — 스칼라 7개

대표님 요구 R6. **7개를 넘기지 않는다.** 변수가 늘면 인격이 아니라 시뮬레이터가 된다.

| 변수 | 타입 | 범위 | 갱신 시점 | 대화에 주는 것 |
|---|---|---|---|---|
| `energy` | int | 0–100 | 슬롯 + 시간대 | 말 길이·활력 |
| `mood` | int | 0–100 | 환경 + 플레이어 대화 | 어투의 결 |
| `focus` | int | 0–100 | 슬롯 | 질문의 깊이 |
| `driveId` | enum ≤6 | `duty` `curiosity` `care` `rest` `growth` `unease` | 일 1회 | **왜 그 말을 먼저 꺼내는가** |
| `goalId` | enum (CSV) | — | 일 1회 | 며칠에 걸친 화제 |
| `goalProgress` | int | 0–100 | 일 1회 | 만족 / 초조 |
| `playerGapDays` | int | 0–30 | 계산(저장 안 함) | 반가움 (서운함 연출 금지 — §11-5) |

**금지**: 슬라이더 UI · 플레이어가 수치를 보는 화면 · 수치 기반 보상. 변수는 **대사의 결을 고르는 내부 값**이다.

### 4-4. 환경 변수 — 기존 관측만

신규 수집 **0**. 전부 기존 ReadTools 화이트리스트 범위이거나 이미 계산된 값이다.

| 환경 | 출처 | 라이프 영향 |
|---|---|---|
| 시간대 (KST) | 시계 | 슬롯 |
| 요일·비번 | 시계 | 근무 축 |
| 현재 행성 | `get_location` | 화제 |
| 행성 코어 R/P/D/T/E | `get_planet_cores` | `mood` / `unease` |
| 스파이 경보 | `get_spy_alert` | `unease` ↑ |
| 마지막 전투 승패 | `get_last_combat` | `mood` ± |
| 오늘 일일 배치 결과 | 기존 배치 상태 1스칼라 | 직무 만족 |
| 팩션 긴장 (스텔리움↔크림슨) | world snapshot에 있을 때만 | `unease` |

**신규 도구는 0~1개.** 배치 결과 읽기 1개만 필요할 수 있고, 그것도 기존 상태에서 파생 가능하면 추가하지 않는다.

### 4-5. 플레이어 대화의 영향 (대표님 명시 요구)

플레이어가 한 말은 두 경로로 라이프에 남는다.

| 경로 | 내용 | 상한 | 수명 |
|---|---|---|---|
| **즉시** | `mood` 델타 (±) | ±10 / 세션 | 당일 |
| **누적** | `anchors` — 기억할 사실 1줄 | **6개 · 각 40자** | L2 (무기한, FIFO 교체) |

anchor 예: 「크림슨 항로를 싫어한다」 · 「호출은 짧은 걸 선호」 · 「다음에 뉴에덴 간다고 했다」.

**anchor에 넣지 않는 것**: 결제·과금 관련 · 실명/개인정보 · 섀도우 짝 닉네임(리빌 전) · 수치화된 호감. 검역은 기존 `quarantineArcCoreChatReply.ts` 원칙을 입력 측에 동일 적용.

## 5. 기억·저장·고도화 (데이터 계약)

### 5-1. 스키마 (설계 표기 — 구현 아님)

**신규 persist 키 1개**: `arcfire_stella_life_v1`

```text
StellaLifeStore
  schemaVersion : 1
  L1 digests[]  : 최대 14  (일 1행)
      d          yyyyMMdd
      mood       0-100
      driveId    enum
      goalId     enum
      done[]     ≤2 · 각 24자   // 그날 한 일
      withPlayer 0|1            // 그날 대화했는가
  L2 core
      traits     { duty, warmth, curiosity, steadiness }  각 0-100 (EMA)
      anchors[]  ≤6 · 각 40자
      narrative  ≤240자 1줄      // "요즘의 스텔라" 한 문장
      sharedDays int
      goalHistory[] ≤4 · 각 goalId + 완료여부
  lastConsolidatedDayKey : string
  lastUpdatedAt : number
```

**바이트 예산**

| 층 | 상한 | 산출 |
|---|---|---|
| L1 | 14행 × ~120B | **≤1.7KB** |
| L2 | traits 4 + anchors 6×40 + narrative 240 + 잡 | **≤1.2KB** |
| **합계** | | **≤3KB** — 테스트로 단언 |

### 5-2. 고도화 교체 규칙 (R4의 핵심)

일 1회 배치(12:00 KST)에서만 실행. 런타임 중 실행 금지.

```text
1. 어제치 digest 1행 생성 → L1 push
2. L1 길이 > 14 이면:
     가장 오래된 1행을 L2에 흡수
       traits   = traits*(1-α) + 그날값*α     α = 0.15
       anchors  = 중요도 유지 · FIFO 6칸
       narrative= 규칙 기반 재작성 (LLM 아님)
     → L1에서 그 행 삭제 (원본 폐기)
3. lastConsolidatedDayKey 갱신
```

**α = 0.15의 뜻**: 하루가 인격을 15%만 민다. 인격이 하루 만에 뒤집히지 않고, 2주면 확실히 달라진다. 「순수 사고능력 고도화에 필요한 데이터만」에 대한 정량적 답이다.

`narrative`는 **규칙 기반으로 재작성**한다. LLM을 부르지 않는다(D2). CSV 문장 템플릿 + traits 구간으로 조합한다.

### 5-3. 보존일 권장

| 항목 | 권장 | 근거 |
|---|---|---|
| L1 보존 | **14일** | 「지난주에 말했던 그거」가 되는 최소 길이. 30일은 용량 대비 대화 기여 낮음 |
| L2 | 무기한 | 고정 크기라 성장하지 않음 |
| L0 | 세션 | persist 안 함 |

14일은 **상수 1개**다. 대표님이 7일/30일을 원하시면 그 숫자만 바꾼다.

### 5-4. purge · game-save · 4곳 세트

김팀장이 친밀도 FSM을 HOLD한 직접 사유가 이것이다. **처음부터 4곳에 등록하고 테스트로 잠근다.**

| # | 지점 | 동작 |
|---|---|---|
| 1 | `purgeLocalAccountData` | **player scope — 계정 초기화 시 purge** (스텔라의 기억은 그 플레이어와의 관계다) |
| 2 | game-save 페이로드 | ≤3KB 포함. 기존 **6시간** 백업 사이클 편승 (`GAME_SAVE_BACKUP_MIN_INTERVAL_MS` · retention 7일) |
| 3 | reload/hydrate | 파싱 실패 시 L2만 초기화, L1은 버림 |
| 4 | `arcCoreMemoryRegistry` (있을 때) | `scope: 'player'` 등록 |

**Firestore 신규 컬렉션 0.** 기존 세이브 문서에 필드로 들어간다. 단발 read/write 계약 그대로, `onSnapshot` 없음.

## 6. 대화 연결 — 질문·생각·대답 3요소

### 6-1. 3요소 정의

대표님 요구 R5. 여기서 **「생각」의 정의를 못 박아야** 기존 잠금과 충돌하지 않는다.

| 요소 | 정의 | 출처 | 출력 형태 |
|---|---|---|---|
| **질문** | 스텔라가 **먼저** 묻는 한 줄 | 슬롯 + goal + anchors | 대사 |
| **생각** | **캐릭터의 내적 독백 한 줄** (연출) | 변수 7개 + 환경 | **대사** |
| **대답** | 플레이어 말에 대한 응답 | 기존 stance/mode | 대사 |

> **중요**: 「생각」은 **모델의 추론 원문(CoT)이 아니다.** `op_persona_output`의 「도구 JSON·사고 원문·시스템 태그 금지」는 그대로 유효하다. 여기서 말하는 생각은 소설의 방백에 해당하는 **연출된 한 줄**이며, 플레이어에게 보이는 대사의 한 종류다. CSV에 `kind=soliloquy` 규칙 행을 추가해 이 구분을 데이터로 고정한다.

**턴당 출력량**: 3개를 매번 내보내지 않는다.

| 상황 | 구성 |
|---|---|
| 기본 | 대답 1 |
| 라이프가 강할 때 | 대답 1 + (생각 또는 질문) 1 |
| 선제 발화(inbound) | 생각 1 + 질문 1 |
| 3개 동시 | **금지** — `op_persona_style` 「평소 두세 문장」 위반 |

### 6-2. 기존 stance / mode와의 매핑 (신규 축 0)

`arcCoreChatDialogueDrive.ts`가 이미 mode 4종 + stance 5종을 고른다. 3요소는 **그 위의 표현 레이어**이지 새 분류기가 아니다.

| 3요소 | 기존 mode | 기존 stance |
|---|---|---|
| 질문 | `lead` | `inquire` |
| 생각 | `clue` | `observe` |
| 대답 | `react` | `observe` / `warn` / `refuse` |

즉 **신규 분류기·신규 CSV 축·신규 정규식 0.** 라이프는 drive에 **입력 하나**(현재 슬롯·변수)를 더 줄 뿐이다.

### 6-3. 팩 주입 — ≤400자

현재 `ARC_CORE_CHAT_MAX_PACK_CHARS = 16_000`. 라이프 블록은 그 2.5% 이내다.

| 블록 | 상한 |
|---|---|
| 지금 하는 일 (슬롯) | 60자 |
| 변수 요약 (energy/mood/drive) | 60자 |
| 오늘 digest | 80자 |
| L2 narrative | 120자 |
| anchors ≤3 (전부 아님) | 80자 |
| **합계** | **≤400자** |

**팩 초과 시 절단 순서**: 라이프 블록이 **가장 먼저** 잘린다. 세계 팩트·페르소나·검역이 우선이다. 라이프가 없어도 대화는 성립해야 한다.

### 6-4. 템플릿(G3) 폴백에서도 작동

대표님 요구 — 「기존 템플릿 대화체계와 이어지는 핵심 사고수준」.

라이프 문장이 **로컬 CSV**이므로 G3 폴백도 같은 재료를 쓴다.

```text
클라우드 LIVE : 라이프 재료 → LLM 자연어 (풍부)
G3 폴백       : 라이프 재료 → 템플릿 슬롯 치환 (담백하지만 같은 사실)
```

오프라인·429·한도 초과에도 **스텔라의 하루는 끊기지 않는다.** 표현의 밀도만 달라진다. 이것이 두 체계를 잇는 지점이다.

## 7. Firebase / 서버리스 최소 구조

대표님 전제 — 스텔라는 독립 서버가 없다. 설계는 그것을 그대로 받는다.

| 축 | 위치 | 비용 |
|---|---|---|
| 라이프 계산 | **클라 로컬** 순수 함수 | 0 |
| 라이프 저장 | **AsyncStorage** (정본) | 0 |
| 클라우드 사본 | 기존 game-save 문서에 ≤3KB 필드 | 기존 **6시간** 백업 사이클에 편승 — **신규 write 0** |
| LLM | 기존 Groq Free + Lambda 1홉 | ZERO_BILL 유지 |
| 신규 Firestore 컬렉션 | **없음** | — |
| 신규 Lambda / 엔드포인트 | **없음** | — |
| `onSnapshot` | **없음** (헌법) | — |

**일일 read/write 증분 = 0.** 라이프는 이미 도는 사이클에 얹힌 필드다.

## 8. 기술적 가능성 — 축별 판정

| 축 | 판정 | 근거 |
|---|---|---|
| 결정론적 가상 시계 | **확실** | 순수 함수 + hash seed. 검증이 쉽고 테스트가 완전 |
| 라이프 CSV | **확실** | 기존 `build:content-tables` 파이프 그대로 |
| 변수 7개 | **확실** | 스칼라 연산. 할당 없음 |
| 3계층 기억 + EMA 합본 | **확실** | 링버퍼 + 가중평균. 알고리즘 난이도 낮음 |
| 팩 주입 400자 | **확실** | 예산 16,000 중 2.5% |
| 3요소 표현 | **높음** | 기존 mode/stance 매핑. 프롬프트 설계 품질에 의존 |
| G3 폴백 정합 | **높음** | 같은 CSV 재료 |
| 일일 배치 훅 | **확실** | 기존 배치에 함수 1개 |
| purge 4곳 | **확실** | 선례 있음(judgment memory) |
| 월드 행동 반영 | **미열림** | D6 — B 스위치 결정 사항 |

**가장 불확실한 축은 프롬프트 품질**이다. 기술이 아니라 문장 설계 문제이며, CSV 반복 수정으로 수렴 가능하다.

## 9. 설계 안정성 — 실패 모드와 방어

| # | 실패 모드 | 증상 | 방어 |
|---|---|---|---|
| F1 | **폰 시계 조작** (앞당김) | 라이프 수십 일 점프 | dayKey **역행 무시** · 1회 진행 **최대 3일 clamp** |
| F2 | 시계 되돌림 | digest 중복 | `lastConsolidatedDayKey` 비교로 멱등 |
| F3 | 장기 미접속(30일+) | L1 전부 만료 | **L2만으로 대화 성립.** 「오랜만」은 세션 1회만 |
| F4 | 슬롯 경계 깜빡임 | 한 세션에 활동이 바뀜 | 슬롯 결과 **세션 1회 캐시** |
| F5 | 팩 초과 | fetch 실패 → G3 | 라이프 블록 **최우선 절단** (§6-3) |
| F6 | purge 누락 | 계정 초기화 후 이전 기억 잔존 | 4곳 세트 + **단언 테스트** |
| F7 | 스키마 변경 | 파싱 예외 | `schemaVersion` + 실패 시 L2 초기화·L1 폐기 |
| F8 | 데이터 성장 | 세이브 비대 | **≤3KB 상한 단언 테스트** |
| F9 | 오프라인 | 라이프 정지? | 로컬 생성이라 **정상 작동** |
| F10 | 무료 티어 429 | 대화 끊김 | G3 폴백 + 같은 라이프 재료 |
| F11 | 라이프-세계 모순 | 「항로 점검했어」인데 그 행성에 없음 | 환경 변수는 **실관측만** 사용. 슬롯 문장은 장소 비특정 |
| F12 | 반복 체감 | 매일 같은 말 | seed에 주차 포함 + goal span 다일 |
| F13 | STAGE 이탈 누수 | 세션 캐시 잔존 | dispose에서 캐시 해제 (신규 리소스 없음) |

**F1과 F8이 가장 중요하다.** 전자는 기능 신뢰를, 후자는 헌법 준수를 결정한다. 둘 다 테스트로 고정 가능하다.

## 10. 적용 현실성 — 단계 S0~S5

각 단계는 **독립 롤백 가능**하고, 앞 단계만으로도 회귀가 없어야 한다.

| 단계 | 산출 | DoD | 대화에 보이나 |
|---|---|---|---|
| **S0** | 본 문서 잠금 · 대표님 결정 5건(§12) 확정 | 문서 REVIEWED | — |
| **S1** | CSV 3장 + `build:content-tables` + **순수 함수 resolver** | `tsc` · 결정론 테스트(같은 seed→같은 출력) · 런타임 연결 **없음** | 아니오 |
| **S2** | 변수 7개 + 환경 바인딩 (기존 ReadTools 재사용) | 스칼라 단위 테스트 · 신규 도구 ≤1 | 아니오 |
| **S3** | L1/L2 스토어 + purge 4곳 + **≤3KB 단언** | 계정 초기화 후 잔존 0 · 바이트 상한 테스트 | 아니오 |
| **S4** | 팩 주입 ≤400자 + 3요소 매핑 | 팩 예산 테스트 · G3 폴백 동일 재료 확인 | **예 — 여기서 처음 체감** |
| **S5** | 일일 배치 정산 훅 (digest + 합본) | 멱등 테스트 · 14일 경과 시뮬 · 배치 시간 증가 ≤50ms | 예 (누적) |

**S1~S3은 플레이어에게 아무것도 보이지 않는다.** 그래도 이 순서여야 한다 — 데이터 계약과 purge를 먼저 잠그지 않으면 S4에서 되돌릴 수 없다. 김팀장이 친밀도 FSM을 HOLD한 이유가 정확히 그것이다.

**최소 실용 지점 = S4.** S5 없이도 「오늘의 스텔라」는 작동한다. S5가 「어제의 스텔라」를 더한다.

구현 착수 전에 이 5개만 확정되면 된다. 나머지는 설계 내부 문제다.

| # | 결정 | 김클로드 권장 | 대안 |
|---|---|---|---|
| 1 | **슬롯 해상도** | **30분 (48슬롯/일)** | 10분(과잉) · 60분(단조) |
| 2 | **L1 최대 보존일** | **14일** | 7일(가벼움) · 30일(용량↑, 기여↓) |
| 3 | **라이프 기억의 purge 범위** | **player scope — 계정 초기화 시 삭제** | world scope 유지(권장 안 함 — 관계 기억이므로) |

1·2번은 **상수 1개**라 실기 후에도 바꿀 수 있다. 3·4·5번은 구조라 뒤집기 비싸다.

## 14. 한 문단 요약

스텔라 아리스에게 **타이머 없는 하루**를 준다. 시계와 CSV와 seed만으로 「지금 무엇을 하고 있는가」가 결정되므로 CPU·배터리·백그라운드 비용이 **0**이다. 하루가 끝나면 일 1회 배치가 그날을 **한 줄로** 접고, 14일이 지난 줄은 인격 수치에 15%씩 녹인 뒤 **버린다**. 그래서 데이터는 **3KB에서 더 자라지 않는다**. 그 기억은 플레이어가 대화를 열 때 **400자**로 팩에 실려, 기존 한 홉 LLM이 **질문·생각·대답**으로 말하게 한다. 오프라인이면 같은 재료로 템플릿이 말한다. 스텔라는 세계를 바꾸지 않는다 — **자기 하루를 살고, 그것을 기억하고, 그 기억으로 말할 뿐이다.**

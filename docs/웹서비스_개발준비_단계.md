## 0. 결론 요약

| 항목 | 판정 |
|------|------|
| 병렬 하이브리드 연결 가능 여부 | **구조적으로 가능** — Metro/Expo가 플랫폼별 확장자(`.web.tsx`)로 빌드 타겟을 가르고, `expo run:ios`/`expo run:android`(EAS)와 `expo export -p web`은 애초에 별도 빌드 파이프라인 |
| "기존 작업 지장 없음"의 성립 조건 | **자동 보장 아님** — 기존 네이티브 전용 파일(Firebase·Skia·`arcfire-native-memory`)을 직접 고치지 않고, **병렬 `.web.ts`/`.web.tsx` 파일 + 플랫폼 어댑터**로 갈라낼 때만 성립 |
| 최대 리스크 | **Skia(STAGE 1·3) 웹 렌더링** — CanvasKit(WASM) 별도 런타임, 이 프로젝트 1순위 규칙(GL ceiling·native_heap)이 전제하는 네이티브 메모리 개념이 브라우저엔 없어 실측 전엔 안전성 불명 |
| 이번 문서의 범위 | **준비 단계만.** Firebase 어댑터·Skia 웹 포팅 등 실제 구현은 **다음 단계**(대표님 승인 후) |

## 1. 배경

대표님 지시(2026-08-20): React Native의 장점을 살려 웹·앱을 동시에 서비스하는 하이브리드 구조를 추구하며, 기존 앱 빌드(iOS/Android)에 지장을 주지 않는 병렬 구조로 웹 서비스를 연결할 수 있는지 확인 요청. 1차 검토(`hybrid-web-app-feasibility-review-20260820`)에서 코드/설정 파일을 직접 확인해 "가능하나 현재 착수점은 0"이라는 결론을 냈고, 이 문서는 그 분석을 **준비 단계 개발 항목**으로 재정리한 것이다. 이번 지시 범위는 **준비 단계까지만** — 이 문서에 나열된 항목 중 실제 실행은 별도 승인 후 진행한다.

## 3. 원칙 (구현 단계에서 반드시 지킬 것)

1. **기존 네이티브 전용 파일 무수정.** Firebase·Skia·`arcfire-native-memory` 관련 기존 `.ts`/`.tsx`는 웹 대응 작업 중 **직접 편집하지 않는다.**
2. **병렬 파일 원칙.** 웹 전용 구현은 `*.web.ts`/`*.web.tsx` 형태로 옆에 추가한다 — Metro가 웹 빌드 시 자동으로 이 파일을 우선 선택하고, iOS/Android 빌드는 기존 파일을 그대로 쓴다(`metro.config.js`는 현재 `getDefaultConfig` 기본값이라 이 동작을 막는 커스터마이징 없음, 확인 완료).
3. **빌드 파이프라인 분리 유지.** `npm run android`/`npm run ios`(및 `preandroid`/EAS 빌드) 스크립트는 그대로 두고, 웹 빌드는 별도 스크립트(`start:web` 등, 준비 단계 항목 1에서 신설)로 완전히 분리한다.
4. **감사 게이트 스캔 목록 불변.** `tools/memory-audit/*`의 하드코딩 파일 목록에 웹 전용 파일을 넣지 않는다 — 네이티브 메모리 규칙과 웹 규칙은 다른 기준이므로 섞지 않는다(웹 자체 기준은 후속 단계에서 별도 정의).
5. **Table-First·CSV·헌법 Top 5 불변.** 웹 지원이 기존 STAGE `replace()`·Skia Zero-Allocation·일 1회 배치 등 절대 금지 규칙을 우회하는 근거가 되지 않는다.

## 4. 준비 단계 개발 항목 (승인 시 진행 범위)

> **이번 지시 범위는 여기까지.** 아래 항목은 "웹이 뭘 지원하는지 실측하고 카탈로그화"하는 단계이며, 실제 기능 구현(Firebase 어댑터 코드, Skia 웹 포팅 코드)은 **포함하지 않는다.**

| # | 항목 | 내용 | 산출물 | 코드 변경 |
|---|------|------|--------|-----------|
| P1 | 웹 타겟 최소 활성화 | `react-native-web`·`react-dom` 설치, `app.json`에 `expo.web` 블록 추가, `package.json`에 `start:web` 스크립트 신설 | 웹 빌드가 최초로 "시도라도 가능한" 상태 | **있음** (신규 추가만, 기존 스크립트/설정 무수정) |
| P2 | `expo start --web` 1회 실측 | 최초 웹 번들 실행, 콘솔 에러·경고 전수 수집(Firebase 모듈 로드 실패, Skia 모듈 로드 실패 등 예상됨) | 실측 로그 + "웹 미대응 지점" 원시 목록 | 없음(실행·기록만) |
| P3 | 웹 미대응 지점 카탈로그 | P2 실측 + 코드 grep으로 Firebase/Skia/`arcfire-native-memory` 호출부를 화면 단위로 분류(허브 STAGE1 / 월드맵 STAGE2 / 전투 STAGE3 / 설정 등) | `docs/`에 카탈로그 표(화면별 웹 차단 요인) | 없음(문서) |
| P4 | Firebase 어댑터 설계안 | native/web 분리 인터페이스 초안 — 어떤 함수를 `.web.ts`로 분리할지, 우선순위(로그인·프로필 read/write 먼저) 정의 | 설계 문서만 (코드 아님) | 없음(문서) |
| P5 | Skia STAGE 웹 스파이크 범위 정의 | 어느 화면부터 웹 렌더링을 시도할지(허브 vs 전투), 최소 스파이크 성공 기준(프레임 안정성·메모리 상한) 정의 | 설계 문서만 (실행은 다음 단계) | 없음(문서) |
| P6 | Firebase Hosting/배포 조사 | 웹 빌드 산출물을 어디에 어떻게 배포할지(Firebase Hosting 등) 옵션 조사만 | 조사 메모 | 없음(문서) |

**P1만 유일하게 실제 파일 변경을 수반**하며, 그마저도 "신규 추가"(패키지 설치·신규 설정 블록·신규 스크립트)뿐이고 기존 파일 내용은 건드리지 않는다. P1 실행 여부도 대표님 별도 확인 후 진행.

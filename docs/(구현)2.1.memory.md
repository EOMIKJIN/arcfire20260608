# Arcfire Online — 메모리 관리 구조 설계서 (Memory Management Spec)

**버전**: v1.0  
**작성일**: 2026-05-13  
**참조**: `1_arcfire_flowchart.txt`, `2_ArcCore_AABS_Final_Spec_v2.2.md`, `rendering-pipeline-baseline.md`, `contents_list_v_01.csv`  
**목적**: 200MB → 800MB로 치솟는 메모리 누적 문제를 구조적으로 해결하기 위한 Cursor 개발 지시서

---

## 0. 문제 진단 요약

### 현상
- 앱 초기 메모리: ~200MB
- 반복 플레이(전투·이동·귀환 사이클) 후: ~800MB
- 결과: 스마트폰 환경에서 앱 크래시

### 근본 원인 (구조적)

```
플레이어 반복 패턴:
Planet Hub → Galaxy Map → Combat → Galaxy Map → Combat → ... → Planet Hub

각 사이클마다 아래 자원이 해제 없이 누적:
  ① Skia Canvas 인스턴스 (PlanetEdenRaidOrbitSkiaCombat)
  ② rAF(requestAnimationFrame) 루프 미취소
  ③ RN Animated 객체 (PlanetTableOrbitMark) 미정지
  ④ postStepRef 콜백 구독 미해제
  ⑤ planetMemoCache 명시적 dispose 미호출
  ⑥ Navigation.navigate() 사용으로 스택 누적 (replace() 미사용)
  ⑦ 콘텐츠(선술집·조선소·무역소 등) 진입 시 하위 컴포넌트 언마운트 미처리
```

## 1. 스테이지 정의 및 메모리 예산

플레이어가 이동하는 모든 스테이지를 명확히 분류하고, 각 스테이지에서 허용되는 메모리 자원을 정의한다.

```
┌─────────────────────────────────────────────────────────┐
│  STAGE 0: Splash / Auth         목표: < 50MB            │
│  STAGE 1: Planet Hub (Main)     목표: < 200MB           │
│  STAGE 2: Galaxy Map            목표: < 120MB           │
│  STAGE 3: Combat                목표: < 250MB           │
│  SUB-STAGE: 행성 시설(선술집·조선소·무역소 등)  목표: < 80MB (Hub 위에서 동작) │
└─────────────────────────────────────────────────────────┘
```

**규칙**: 스테이지 전환 시 이전 스테이지의 메모리 예산은 반드시 해제 후 다음 스테이지를 초기화한다.

## 2. 플레이어 반복 패턴 분석

contents_list에 정의된 콘텐츠를 플레이어 행동 사이클 기준으로 분류한다.

### 2-1. 고빈도 반복 사이클 (메모리 누적 위험 최고)

```
[전투 루프] — 가장 빈번, 메모리 위험 1순위
Planet Hub → Galaxy Map → 필드 전투 → Galaxy Map → 필드 전투 → ... → Planet Hub
  포함 콘텐츠: 필드 전투, 은신처 소탕, 공성/수성전

[성장 루프] — 전투 루프와 혼합
전투 → 전리품 획득 → 행성 복귀 → 선술집(용병모집) → 조선소(함선업그레이드) → 재출격
  포함 콘텐츠: 용병 모집/고용, 부대 육성, 포로 관리, 대장기술
```

### 2-2. 중빈도 사이클 (메모리 위험 2순위)

```
[경제 루프]
Planet Hub → 무역소 진입 → 교역/수송단 → 복귀 (세션 내 반복)
  포함 콘텐츠: 교역(무역), 작업장 운영, 수송단 구성

[미션/사회 루프]
행성 NPC 퀘스트 수락 → 이동 → 목표 완료(전투 혹은 교역) → 복귀 → 보상
  포함 콘텐츠: 퀘스트, 토너먼트
```

### 2-3. 저빈도 사이클 (장기 누적 위험)

```
[경영/정치/외교 루프]
도시 관리 → 정책 수립 → 가문 등급 관리 → 동료 영입 → 외교 행동
  포함 콘텐츠: 도시 관리, 정책 수립, 가문 등급, 동료 영입, 결혼/가문, 국가 건국
```

**결론**: 전투 루프(고빈도)가 메모리 누적의 핵심 원인. 이 사이클에 대한 완벽한 해제 구조가 최우선이다.

## 3. 핵심 설계 원칙 (절대 규칙)

### 원칙 1: Navigation.replace() 강제

모든 주요 스테이지 전환은 `Navigation.replace()`를 사용한다. `navigate()`는 스택을 쌓아 이전 스테이지 컴포넌트가 언마운트되지 않으므로 사용 금지.

```
허용:  Navigation.replace('PlanetHub')
       Navigation.replace('GalaxyMap')
       Navigation.replace('Combat')
금지:  Navigation.navigate('PlanetHub')  // 스택 누적 → 메모리 누수
```

**예외**: 행성 내부 시설(선술집·조선소·무역소·퀘스트 등 SUB-STAGE)은 Modal 또는 BottomSheet로 구현하여 Hub를 언마운트하지 않고 오버레이 방식으로 처리. SUB-STAGE 닫힘 시 반드시 자체 cleanup 수행.

---

### 원칙 2: useStageMemory 훅 — 모든 스테이지 공통 계약

모든 스테이지 루트 컴포넌트는 아래 훅 계약을 준수한다.

```typescript
// hooks/useStageMemory.ts

/**
 * 스테이지 진입/이탈 시 메모리를 관리하는 공통 훅.
 * 모든 주요 스테이지 컴포넌트의 최상단에서 호출해야 한다.
 *
 * @param stageId - 스테이지 식별자 (로그 및 디버깅용)
 * @param onMount - 스테이지 진입 시 자원 초기화 함수
 * @param onUnmount - 스테이지 이탈 시 자원 해제 함수 (누락 금지)
 */
export function useStageMemory(
  stageId: string,
  onMount: () => void | Promise<void>,
  onUnmount: () => void,
): void

// 사용 예시
useStageMemory(
  'COMBAT',
  () => {
    registerCombatResources();
    subscribeCombatCallbacks();
  },
  () => {
    disposeCombatResources();   // Skia canvas 해제
    cancelAllAnimationFrames(); // rAF 루프 종료
    unsubscribeCallbacks();     // postStepRef 구독 해제
  }
);
```

---

### 원칙 3: dispose() 체이닝 — 자원 등록과 해제는 항상 쌍으로

자원을 등록하는 코드 바로 아래에 dispose 코드를 작성한다. 등록만 있고 해제가 없는 코드는 허용하지 않는다.

```typescript
// 올바른 패턴
useEffect(() => {
  const rafId = requestAnimationFrame(renderLoop);
  const subscription = eventEmitter.addListener('step', onStep);

  return () => {
    cancelAnimationFrame(rafId);    // rAF 반드시 취소
    subscription.remove();           // 이벤트 리스너 해제
  };
}, []);

// 금지 패턴 (cleanup 없음)
useEffect(() => {
  requestAnimationFrame(renderLoop); // rafId를 저장하지 않아 취소 불가
}, []);
```

---

### 원칙 4: planetMemoCache 범위 제한

`planetMemoCache`는 현재 행성 세션에 종속된 휘발성 캐시다.

```typescript
// 허용: 현재 행성 세션 데이터
planetMemoCache.set('nearbyNpcs', [...]);
planetMemoCache.set('orbitPositions', [...]);

// 금지: 영속 데이터를 memoCache에 저장
planetMemoCache.set('playerProfile', profile); // → planetCoreRuntimeStore 사용

// 세션 종료 시 전체 초기화 (dispose에서 반드시 호출)
planetMemoCache.clear();
```

**`planetCoreRuntimeStore`**: 앱 전체 생명주기 동안 유지되는 영속 스토어. 행성 세션 dispose 대상에서 제외.

## 4. 스테이지별 상세 메모리 관리 계약

### 4-1. STAGE 1: Planet Hub (Main Stage)

**진입 시 (`onMount`)**
```
1. registerPlanetSessionResource() 호출
2. CSV 인덱스 캐시(Map<shipId, index>) 확인 — 이미 빌드된 경우 재사용
3. PlanetHubOrbitSkiaLayer 초기화
4. orbitClockMs rAF 루프 시작 (rafId 저장 필수)
5. 거리 정렬 타이머 시작 (INFO_DISTANCE_SORT_INTERVAL_MS, 현재 5000ms)
```

**이탈 시 (`onUnmount`)**
```
1. cancelAnimationFrame(rafId) — orbitClockMs 루프 종료
2. clearInterval(distanceSortTimer) — 거리 정렬 타이머 종료
3. PlanetHubOrbitSkiaLayer.dispose() — Skia canvas 해제
4. PlanetTableOrbitMark 애니메이션 전체 정지 (Animated.stop())
5. planetMemoCache.clear() — 세션 캐시 초기화
6. nearbyNpcList 참조 해제 (null 할당)
```

**SUB-STAGE 관리 (선술집 · 조선소 · 무역소 · 퀘스트 · 토너먼트 등)**

Hub는 언마운트하지 않고 Modal/BottomSheet 오버레이로 구현.
```
진입: Modal.present() — Hub rAF 루프는 유지 (배경 애니메이션 지속)
      단, Hub의 거리 정렬 타이머는 일시 정지 가능 (불필요한 CPU 절약)
이탈: Modal.dismiss() → 각 시설 컴포넌트의 자체 cleanup 실행
      (시설별 로컬 상태, 폼 데이터, 임시 캐시 해제)
```

---

### 4-2. STAGE 2: Galaxy Map

**진입 시**
```
1. beginPlanetHubSuspendingNavigation() 호출
2. 은하계 지도 정적 데이터 로드 (CSV 인덱스 재활용, 재인덱싱 금지)
3. 이동 시뮬레이션 타이머 시작
```

**이탈 시**
```
1. 이동 시뮬레이션 타이머 정지
2. 은하계 지도 렌더링 상태 초기화
3. 로컬 이동 경로 배열 참조 해제
```

**중요**: Galaxy Map은 메모리 예산이 낮다(목표 120MB). 전투 진입 전 Galaxy Map 자원을 먼저 해제하고 Combat을 초기화한다.

---

### 4-3. STAGE 3: Combat (PlanetEdenRaidOrbitSkiaCombat)

가장 중요한 스테이지. 반복 진입 시 누적 위험이 최고다.

**진입 시**
```
1. 전투 자산 초기화 (함선, 미사일, 궤적 배열)
2. PlanetEdenRaidOrbitSkiaCombat Skia canvas 초기화
3. combatOrbitPostStepRef 콜백 등록
4. 시뮬레이션 루프 시작 (PlanetEdenRaidTestLayer)
```

**이탈 시 — 전투 종료마다 반드시 실행**
```
1. 시뮬레이션 루프 정지
2. combatOrbitPostStepRef.current = null  ← 콜백 참조 해제 필수
3. PlanetEdenRaidOrbitSkiaCombat.dispose() ← Skia canvas 명시적 해제
4. 미사일 배열 초기화: missiles.length = 0
5. 함선 객체 배열 참조 해제
6. cancelAnimationFrame(combatRafId)
7. DISPOSE_COMBAT_ASSETS 완료 후 Navigation.replace() 호출
```

**미사일 시각 규칙 (rendering-pipeline-baseline 준수)**
```typescript
// 미사일 탄두는 명중 즉시 제거, 궤적만 잔상 유지
const shouldRenderHead = !m.hitApplied;
// 이 조건은 수정 금지 (Rendering Pipeline Baseline §4 준수)
```

## 5. CSV 정적 인덱스 관리

### 앱 생명주기 전체에서 단 1회만 빌드

```typescript
// store/staticTableStore.ts

/**
 * 앱 부트스트랩 시 단 1회 실행. 이후 재인덱싱 금지.
 * Table-First 원칙: CSV 정본 데이터는 절대 수정하지 않는다.
 */
const shipMap = new Map<string, ShipRow>();
const weaponMap = new Map<string, WeaponRow>();
const npcMap = new Map<string, NpcRow>();

export function buildStaticIndexes(csvData: CsvBundle): void {
  csvData.ships.forEach(row => shipMap.set(row.id, row));
  csvData.weapons.forEach(row => weaponMap.set(row.id, row));
  csvData.npcs.forEach(row => npcMap.set(row.id, row));
}

// O(1) 조회 — forEach/findIndex 사용 금지
export const getShip = (id: string) => shipMap.get(id);
export const getWeapon = (id: string) => weaponMap.get(id);
export const getNpc = (id: string) => npcMap.get(id);
```

**규칙**:
- `shipMap`, `weaponMap`, `npcMap`은 앱 전체 생명주기 동안 유지 (dispose 대상 제외)
- 스테이지 전환 시 재인덱싱 금지 — 부트스트랩 시 1회만 실행
- CSV 정본은 수정 금지, AABS 보정은 `planetCoreRuntimeStore`의 GlobalMultiplier만 조정

## 6. RN Animated 관리 규칙

`PlanetTableOrbitMark` 등 RN Animated 기반 마커는 다음 규칙을 따른다.

```typescript
// 올바른 패턴
const animX = useRef(new Animated.Value(0)).current;
const animY = useRef(new Animated.Value(0)).current;

useEffect(() => {
  const anim = Animated.loop(
    Animated.sequence([...])
  );
  anim.start();

  return () => {
    anim.stop();         // 애니메이션 정지
    animX.setValue(0);   // 값 초기화 (참조는 유지, 재사용 가능)
    animY.setValue(0);
  };
}, []);
```

**금지 패턴**:
```typescript
// useRef 없이 매 렌더마다 new Animated.Value() 생성 — 메모리 누수
const animX = new Animated.Value(0); // 컴포넌트 외부 또는 렌더 함수 내 직접 선언 금지
```

**위치 이동 규칙 (rendering-pipeline-baseline 준수)**:
- `transform: [{ translateX }, { translateY }]` 사용 (layout `left`/`top` 금지)
- Captain 캡션은 마커 하단에 렌더링 (`orbitShipCaption`)

## 7. Skia 레이어 관리 규칙

```typescript
// PlanetHubOrbitSkiaLayer 및 PlanetEdenRaidOrbitSkiaCombat 공통 규칙

// ① Canvas ref는 컴포넌트 언마운트 시 반드시 해제
const canvasRef = useRef<SkiaCanvas>(null);

useEffect(() => {
  return () => {
    canvasRef.current?.dispose?.(); // Skia canvas dispose
  };
}, []);

// ② Arc packing 업데이트는 구조 시그니처(signature) 변경 시에만 실행
//    매 프레임 repack 금지 (rendering-pipeline-baseline §1 준수)
if (currentSignature !== prevSignatureRef.current) {
  repackArcs();
  prevSignatureRef.current = currentSignature;
}

// ③ 독립 rAF 루프 금지 (Combat 한정)
//    시뮬레이션 postStepRef 콜백을 통해서만 렌더 트리거
//    별도 rAF로 Combat Skia를 구동하면 시뮬레이션과 desync 발생
```

**허브·전투 Skia** (`PlanetHubOrbitSkiaLayer`, `PlanetEdenRaidOrbitSkiaCombat`)는 Combat Picture pool과 **별도 worklet 계약**을 따른다.  
→ `docs/(구현)SKIA_WORKLET_MEMORY_CONTRACT.md` · `npm run audit:skia-memory`  
(worklet SharedValue Path에는 `dispose()` 금지 — Combat Picture pool과 혼동 금지)

## 8. 콘텐츠 확장 시 메모리 관리 체크리스트

contents_list에 정의된 신규 콘텐츠를 추가할 때 반드시 아래를 점검한다.

| 콘텐츠 분류 | 스테이지 | 진입 방식 | Cleanup 요구사항 |
|---|---|---|---|
| 필드 전투 / 은신처 소탕 / 공성전 | STAGE 3 (Combat) | Navigation.replace() | Skia dispose + rAF 취소 + 콜백 null |
| 용병 모집 / 부대 육성 / 포로 관리 | SUB-STAGE (Hub Modal) | Modal.present() | 모달 자체 상태 초기화 |
| 교역 / 작업장 / 수송단 | SUB-STAGE (Hub Modal) | Modal.present() | 교역 캐시 해제 |
| 대장기술 (무기 제작) | SUB-STAGE (Hub Modal) | Modal.present() | 제작 폼 상태 해제 |
| 도시 관리 / 정책 수립 | SUB-STAGE (Hub Modal) | Modal.present() | 정책 로컬 상태 초기화 |
| 가문 등급 / 동료 영입 | SUB-STAGE (Hub Modal) | Modal.present() | NPC 리스트 참조 해제 |
| 결혼·가문 / 국가 건국 | SUB-STAGE (Hub Modal) | Modal.present() | 외교 상태 초기화 |
| 퀘스트 | SUB-STAGE (Hub Modal) | Modal.present() | 퀘스트 진행 상태 저장 후 로컬 해제 |
| 토너먼트 | STAGE 3 (Combat 변형) | Navigation.replace() | Combat과 동일한 Cleanup |
| 약탈/범죄 | STAGE 3 (Combat 변형) | Navigation.replace() | Combat과 동일한 Cleanup |

## 9. 거리 정렬 성능 규칙

```typescript
// INFO_DISTANCE_SORT_INTERVAL_MS = 5000 (현재값 유지)
// 매 프레임 sort 금지 — 5초 간격 스로틀링 준수 (rendering-pipeline-baseline §2)

const distanceSortTimer = setInterval(() => {
  sortByDistance();
}, INFO_DISTANCE_SORT_INTERVAL_MS);

// 스테이지 이탈 시
clearInterval(distanceSortTimer);

// Arc 조회는 반드시 O(1) Map 사용
const arcShip = arcShipMap.get(shipId); // O(1)
// const arcShip = arcShipList.findIndex(...); // 금지 — O(n)
```

## 10. AABS 보정값과 메모리

AABS(능동 밸런싱 시스템)의 보정값은 메모리 관리 측면에서 다음 규칙을 따른다.

```
보정값 저장 위치: planetCoreRuntimeStore (영속, dispose 제외 대상)
보정 범위: 1회 최대 5%, 누적 ±15% 이내
safeModeEnabled 발동 시: 모든 보정값을 1.0(정본)으로 강제 복구

보정값은 메모리에 상주하지만 크기가 작다 (스칼라 계수값만 보관).
effectPending / pending 상태 아이템은 보정 대상 제외 — 관련 캐시 생성 금지.
```

## 14. 절대 금지 사항 (Do Not Drift)

아래 항목은 어떠한 이유로도 변경하거나 우회하지 않는다.

```
① CSV 정본 데이터 직접 수정 금지 (AABS GlobalMultiplier만 사용)
② Navigation.navigate() 사용으로 스택 누적 금지
③ Combat Skia에 독립 rAF 루프 추가 금지 (postStepRef 콜백 방식 유지)
④ 미사일 탄두 제거 조건(!m.hitApplied) 변경 금지
⑤ 거리 정렬을 매 프레임 실행 금지 (INFO_DISTANCE_SORT_INTERVAL_MS 준수)
⑥ table NPC 위치 이동을 layout left/top 방식으로 변경 금지 (transform 유지)
⑦ arc 조회를 findIndex() O(n)으로 구현 금지 (Map O(1) 유지)
```

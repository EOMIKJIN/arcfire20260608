# NPC 자유대화 시스템 — 아키텍처 재설계 검토 문서

## 0. 문서의 목적

커서(Cursor)가 "NPC 자유대화 기능 구현에는 AWS가 필요하다"는 주장을 제시했습니다.
본 문서는 이 주장을 **기존 프로젝트 마스터 스펙 근거와 대조하여 검증**하고, 커서가 구체적으로
① AWS가 필요하다고 판단한 근거를 명시하도록 요구하며, ② 근거가 없거나 불충분할 경우 채택할
**서버리스 + Anthropic API 직접 호출** 대안 설계를 실행 가능한 수준으로 명세합니다.

> ⚠️ **본 문서 작성자(기획/PM) 확인 사항**: 커서가 제시한 "AWS 필요" 근거의 구체적 내용(예: 특정 SDK,
> 특정 인프라 제약, 특정 보안 요구사항)은 현재 대화 시점에 전달되지 않았습니다. 따라서 아래 §1은
> "추정 가능한 근거 목록 + 각 근거의 타당성 검토"로 구성했으며, **커서는 반드시 §1의 체크리스트에
> 답하여 실제 근거를 명시해야 합니다.** 근거 없이 AWS를 전제로 코드를 작성하지 마십시오.

## 1. 커서의 "AWS 필요" 주장 검증 체크리스트

커서는 아래 항목에 **Yes/No + 구체적 이유**로 답변한 뒤 작업을 시작합니다. 근거 없는 항목은 "No"로
간주하고 서버리스(§3) 설계를 그대로 따릅니다.

| # | 가능한 근거 | 프로젝트 문서상 실제 근거 | 타당성 |
|---|------|------|------|
| 1 | "게임 서버가 이미 AWS 기반이라 통합이 쉽다" | **근거 없음.** 마스터 스펙 §0-1: "서버 구조: 서버리스 — 전용 게임 서버 없음. Firestore(유저 데이터) + 클라이언트 로컬 AI(ArcCore) 처리." AWS 언급 전무. | ❌ 기각 |
| 2 | "AgentCore 등 복잡한 에이전트 프레임워크가 필요하다" | 본 기능은 텍스트 응답만으로 충분(사용자 확인 사항 §3). 이미지·음성 생성, 멀티스텝 툴 체인 불필요. | ❌ 기각 (과설계) |
| 3 | "대량 동시 접속 처리를 위한 오토스케일링이 필요하다" | 아크파이어는 **싱글플레이 샌드박스**(마스터 스펙 §0-1). 실유저 간 네트워크 상호작용 없음 → 대량 동시 접속 시나리오 자체가 존재하지 않음. | ❌ 기각 (해당 없음) |
| 4 | "이미 AWS 계정·IAM·VPC 등 인프라가 구축돼 있다" | 프로젝트 어떤 문서에도 AWS 계정/리소스 존재 언급 없음. | ⚠️ 커서가 실제 존재 여부를 **명시적으로 답변**해야 함 |
| 5 | "Firebase Functions는 콜드스타트/리전 제약이 있어 AWS Lambda가 낫다" | 기술적으로 논쟁 가능하나, 이미 Firebase(Firestore)를 쓰고 있어 **신규 벤더 추가 자체가 비용**(계정 관리, 키 관리, 청구 채널 이원화). | ⚠️ 성능 수치 근거 제시 시에만 재검토 |
| 6 | "규정/보안 컴플라이언스상 AWS가 요구된다" | 문서상 근거 없음. | ⚠️ 커서가 어떤 규정인지 명시해야 함 |

**결론(잠정)**: 현재 확인 가능한 근거로는 AWS 도입을 정당화할 사유가 없습니다. 커서는 위 표의 ⚠️ 항목에
대해 구체적 근거를 제시하지 못하면, **§3의 서버리스(벤더 중립/Firebase Functions 우선) 설계로 진행**합니다.

## 2. 기존 프로젝트 아키텍처 원칙과의 정합성 (재확인)

| 마스터 스펙 원칙 | 내용 | 본 기능과의 관계 |
|---|---|---|
| 서버리스 (§0-1) | "전용 게임 서버 없음" | Claude API 호출용 **경량 프록시 함수 1개**는 이 원칙에 반하지 않음(게임 서버가 아니라 API 키 은닉용 프록시) |
| Local-AI-First (§1) | 밸런스·전투·트래픽은 100% 클라이언트 로컬 연산 | NPC 대화는 이 범주 밖(신규 기능) — 단, **오프라인 시 로컬 폴백** 필요(§4-3) |
| Firestore 역할 최소화 (§0-3) | 단발성 프로필 동기화만 허용, 실시간 동기화 금지 | 대화 로그를 Firestore에 실시간 스트리밍하지 말 것. 저장 시에도 단발성 write만 |
| 오프라인 플레이 (§0-1) | "세계 시뮬레이션은 100% 로컬 → 오프라인 가능"이 핵심 상품 강점 | 네트워크 필요한 유일한 기능이 되므로, 반드시 **네트워크 미가용 시 성능 저하 없는 폴백** 설계 필수 |

## 3. 채택 아키텍처 (AWS 불필요 시 기본안)

```
[React Native 클라이언트]
   │  (평문 프롬프트 + 대화 컨텍스트만 전송, API 키 없음)
   ▼
[서버리스 함수 1개] ── 인증(옵션) → Anthropic API 호출 → 응답 프록시
   │  환경변수: ANTHROPIC_API_KEY (Anthropic Console/platform.claude.com 발급)
   ▼
[Anthropic API: /v1/messages]
```

### 3-1. 플랫폼 선택

- **문서상 확정 사실 없음** — 프로젝트는 아직 이 부분을 명시한 적이 없습니다.
- **권장(사실 기반 근거 있음)**: 프로젝트가 이미 **Firebase(Firestore)** 를 사용 중이므로,
  **Firebase Cloud Functions**를 우선 검토합니다. 신규 벤더/계정/청구 채널을 늘리지 않기 때문입니다.
- 커서가 Vercel/Cloudflare Workers/Supabase Edge Functions 등 다른 플랫폼을 원할 경우,
  §1 체크리스트와 동일한 형식으로 **비교 근거(콜드스타트, 리전, 무료 티어, 기존 스택과의 통합 비용)**
  를 제시한 뒤 결정합니다. 특정 플랫폼을 임의로 가정하고 코드를 작성하지 않습니다.

### 3-2. 보안 원칙 (필수)

1. `ANTHROPIC_API_KEY`는 **서버리스 함수 환경변수에만 존재**. 클라이언트 번들·AsyncStorage·Firestore
   어디에도 저장/로그 금지.
2. 클라이언트 → 서버리스 함수 요청에는 **Rate limit + (가능하면) Firebase Auth 토큰 검증**을 적용해
   키 남용(요금 폭탄)을 방지합니다. 이는 리스크 레지스터 R-01(클라이언트 위조) 패턴과 동일한 위험군이므로
   동일한 완화책(서버 측 검증)을 적용합니다.
3. 대화 프롬프트에 유저 개인정보(uid 외)를 과도하게 포함하지 않습니다.

## 4. 구현 상세 지시 (커서 작업 단위)

### 4-1. 서버리스 함수 스펙

```
POST /api/npc-chat
Request:
{
  "npcId": "string",          // tables/content/npc_ai_ships.csv 등 정본 NPC ID (허용 목록만)
  "playerMessage": "string",
  "conversationHistory": [ { "role": "user"|"assistant", "content": "string" } ], // 최근 N턴만
  "playerContext": { "level": number, "location": "string" } // 선택적, 세계관 반영용
}

Response:
{
  "npcReply": "string",
  "conversationId": "string"
}
```

- 함수 내부에서만 `messages: [...history, {role:"user", content: playerMessage}]` 구성 후
  `model: "claude-sonnet-4-6"`(또는 운영 확정 모델) 호출.
- **NPC별 system prompt는 함수 내부에 하드코딩하지 않고**, `tables/content/` 정본 원칙(Table-First)에
  맞춰 신규 CSV(예: `npc_dialogue_persona.csv`)로 관리 — NPC 성격/말투/세계관 제약을 데이터화.

### 4-2. 대상 NPC 범위 (중요 — 전체 적용 금지)

- `npc_ai_ships.csv`(223건)는 **궤도 트래픽/전투용 장식 AI**이며 대화 상호작용 대상이 아닙니다.
  전체 NPC에 LLM 대화를 붙이는 것은 과설계이자 비용 낭비입니다.
- 적용 대상은 **허브 시설의 상호작용 가능 NPC**(바·조선소·무역소 등, 기존 "Governor System"
  핵심 NPC)로 한정합니다. 정확한 대상 목록은 기획 확정 후 별도 CSV로 관리합니다.

### 4-3. 오프라인 폴백 (필수 — 미구현 시 릴리스 불가)

- 네트워크 미가용/API 오류 시, 기존 스펙의 **선택지 기반 대화(Branching Dialogue)** 로 자동 전환합니다.
- 클라이언트는 서버리스 함수 응답을 **타임아웃(예: 8초)** 내 받지 못하면 폴백 UI를 노출합니다.
- 이 기능이 "오프라인 플레이 가능"이라는 기존 상품 강점을 훼손하지 않도록, **자유대화는 온라인 전용
  부가 기능**임을 UI 상에서 명확히 표시합니다(예: 네트워크 아이콘, "대화 연결 중" 상태).

### 4-4. 로컬 상태/메모리 계약 준수

- 대화 세션 상태는 `planetMemoCache` 패턴(스테이지 이탈 시 `.clear()`)을 따릅니다.
- Firestore에 대화 로그를 저장할 경우 **단발성 write만** 허용(§0-3 원칙), `onSnapshot` 등 실시간 구독 금지.

### 4-5. 비용/성능 가드레일

- 서버리스 함수에 **분당/일일 호출 상한**을 두어 요금 폭주를 방지합니다(마스터 스펙 §1 "파이어베이스
  통신 요금 폭탄" 리스크와 동일한 클래스의 위험).
- `conversationHistory`는 최근 N턴(예: 6턴)으로 제한해 토큰 비용을 통제합니다.

## 5. 커서에게 요구하는 산출물

1. §1 체크리스트에 대한 **명시적 답변**(AWS가 실제로 필요한 근거가 있다면 무엇인지).
2. 근거가 불충분할 경우, §3~4에 따른 **서버리스 함수 초안 코드**(Firebase Functions 기준, 다른 플랫폼
   제안 시 근거 포함) 및 클라이언트 호출 훅(`useNpcChat` 등) 설계안.
3. `npc_dialogue_persona.csv` 스키마 초안 (Table-First 원칙 준수).
4. 오프라인 폴백 UI/로직 흐름도(간단한 텍스트 다이어그램으로 충분).

> 본 문서에서 다루지 않은 세부사항(정확한 CSV 컬럼, 서버리스 함수 리전, Rate limit 수치 등)은
> 기획 확정 전까지 **추측하여 구현하지 말고 별도 확인 요청**할 것.

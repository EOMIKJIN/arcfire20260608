# 바 종업원 유니크 초상 — 로딩 전략 검토 (2026-09-06)

> **결론 먼저**: 실현 가능. **새 아키텍처가 필요 없다** — 지금 5장을 순환시키는 맵 파일을 나중에 288장(또는 그 이상) 고유 `require()`로 바꾸기만 하면 된다. 진짜 비용은 런타임 메모리가 아니라 **앱 번들 용량**이고, 이건 원본 이미지 크기 관리로 해결한다.

---

## 1. 대표님 질문 요지

향후 모든 종업원(현재 288명, 은하 확장 시 더 늘 수 있음)이 개별 유니크 이미지를 가져야 하는데, 한 바에 동시에 보이는 인원은 최대 ~20명을 넘지 않으니 이 특성을 살려 **바 단위로 효율적으로 로딩**할 수 있는지 검토.

## 2. 현재 구조 재확인

- `src/game/barAttendantPortraitAssets.ts`: `bar_att_portrait_001`~ 키를 `bar_att_char006~015.png` **10장 순환** (픽셀 규격 **240×240**).
- `src/components/bar/BarPatronageLoungeTab.tsx`: 현재 바(`buildBarPatronageRoster`)의 로스터만 렌더 — **행성당 12~20명, 전체 288명 중 극히 일부만 화면에 마운트**.
- 이미 존재하는 동일 패턴: `src/game/npcCaptainPortraitAssets.ts`(NPC 함장 초상) + `docs/NPC_CAPTAIN_PORTRAIT_ASSET_CONTRACT.md`(운영 계약) — "키 → `require()`" 플랫 맵 + 온디맨드 `<Image>` + 부트 prefetch 목록(`listCriticalSessionImageSources`)에서 **명시적으로 제외**.

## 3. 왜 "바 단위 로딩"이 이미 공짜로 되는가

RN/Metro의 두 가지 성질이 이 문제를 이미 풀어준다.

| 성질 | 의미 |
|------|------|
| `require()`는 **빌드타임 정적 링크**만 한다 | 288개를 전부 맵에 등록해도, **화면에 마운트되지 않은 `<Image>`는 런타임에 디코드되지 않는다.** 맵에 몇 줄이 있는지는 런타임 메모리와 무관 — 앱 번들(설치 파일) 크기에만 영향. |
| `<Image>`는 **마운트 시점에만 비트맵 디코드** | `BarPatronageLoungeTab`이 이미 "그 행성 로스터만" 렌더하므로(§2), 동시에 화면에 존재하는 초상은 항상 **로스터 크기(12~20)**로 자연스럽게 상한선이 걸린다. 288장이든 2880장이든 카탈로그 크기와 무관. |

즉, "바 기준으로 효율적으로 로딩"이라는 목표는 **이미 지금 코드 구조가 만족**하고 있다. 별도의 지연로딩(lazy chunk)·페이지네이션 인프라를 새로 만들 필요가 없다 — 지금 5장을 순환시키는 맵을 288장 유니크 `require()`로 교체하기만 하면 된다.

## 4. 진짜 신경 써야 할 것 — 런타임 메모리가 아니라 **앱 번들 용량**

기존 임시 초상 PNG 실측(참고용):

| 파일 | 용량·규격 |
|------|------|
| `bar_att_char006~015.png` | **240×240** 정본 샘플 |
| `noname` / `stella` / `mia` 함장 초상 | **240×240** 통일 |

이 값 그대로 288장을 만들면 **288 × 평균 200KB ≈ 55MB**가 앱 설치 용량에 그대로 얹힌다 — 결코 작지 않다. 반면 이 파일들은 `NPC_CAPTAIN_PORTRAIT_ASSET_CONTRACT.md` §6이 이미 권장한 "대화 145px contain · 과도한 해상도 금지" 기준보다 훨씬 큰, **최적화 이전 원본**으로 보인다. 실제 표시 크기(라운지 썸네일 72px, 공연 화면 프레임 252px 높이)에 맞춰 제작하면 장당 20~40KB대로 충분히 줄일 수 있어, 288장 기준 **6~12MB**로 낮아진다.

**권장**: 원화 발주 전 **240×240 PNG** (`docs/NPC_CAPTAIN_PORTRAIT_ASSET_CONTRACT.md` §0) 고정. 표시는 UI `contain` 스케일.

## 5. 운영 리스크 — 수작업 288줄보다 자동화

지금처럼 `BAR_ATTENDANT_PORTRAIT_BY_KEY` 맵에 288줄을 손으로 채우면 오타·누락이 나기 쉽고, CSV의 `portraitImageAssetKey`와 실제 파일이 어긋나도 **조용히 표시만 안 될 뿐 빌드가 안 깨진다**(Metro 정적 require 특성상 CSV만 채우고 맵/파일이 없으면 자동 폴백되어 오류로 드러나지 않음).

**권장 2가지**(이미 이 프로젝트에 있는 패턴 재사용):
1. **맵 파일 자동 생성**: `tools/content-tables/seed-bar-attendants-galaxy.mjs`와 같은 방식으로, `assets/images/bar/` 폴더를 스캔해 `barAttendantPortraitAssets.ts`를 자동 생성하는 빌드 스크립트 추가 — 파일이 있으면 유니크 require, 없으면 지금처럼 5장 순환 폴백(점진적 마이그레이션 가능).
2. **감사 스크립트**: `npm run audit:npc-captain-portraits`와 동일한 패턴으로 `audit:bar-attendant-portraits`를 만들어, CSV의 288개 키가 전부 맵/파일에 존재하는지 CI에서 확인(불일치 시 exit 1).

이렇게 하면 원화가 몇 장씩 들어와도(전부 한꺼번에가 아니라 점진적으로) 자동으로 반영되고, 빠진 게 있어도 조용히 넘어가지 않는다.

## 6. 추가로 확인한 사소한 개선점

`BarPatronageLoungeTab.tsx`·`BarPatronagePerformView.tsx`의 `<Image>`가 현재 `resizeMode="cover"`만 쓰고 **`resizeMethod="resize"`(안드로이드 네이티브 다운샘플 디코드)가 빠져 있음**을 확인했다. 지금은 5장 재사용이라 체감 차이가 없지만, 288장 유니크 이미지로 바뀌면 안드로이드에서 원본 해상도 그대로 디코드 후 축소하는 비용이 실제로 발생한다. 유니크 이미지 도입과 같은 타이밍에 이 prop만 추가하면(로직 변경 없음) 안전하게 예방된다.

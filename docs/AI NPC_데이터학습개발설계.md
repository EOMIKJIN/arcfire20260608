# 아크파이어 — NPC AI 데이터 학습·처리 시스템

> 투자자용 제안서(arcfire-mobile-intro.html/jsx) 및 "AI 멀티플레이체감 시스템 설계" MD와는 별도로 관리되는, NPC AI 대화 데이터 파이프라인 전용 설계 문서.

---

## 0. 개발 목적

**이 개발의 목적은 게임 속에서 최고 성능의 NPC AI 데이터를 확보하고, 그 성능을 유지하여, 시장 수요까지 확보하는 것이다.**

세 단계로 풀어보면:
1. **데이터 확보** — 유저와 NPC 간 실제 대화가 쌓이면서, 어떤 대화가 몰입감을 주는지·어떤 요청이 템플릿으로 커버되지 않는지에 대한 실증 데이터가 축적된다.
2. **성능 유지** — 이 데이터를 지속적으로 모니터링·개선에 활용해, 시간이 지나도 NPC 대화 품질이 떨어지지 않도록 유지한다.
3. **시장 수요 확보** — 대화 품질 자체가 유저 재접속·과금의 핵심 차별점이 되고, 검증된 파이프라인은 다른 게임사에도 라이선싱 가능한 기술 자산이 된다.

---

## 1. 핵심 원칙 (오해 방지)

유저와 AI(NPC) 간 대화가 쌓이는 과정은 **기반 모델 자체를 재학습시키는 것이 아니라, 대화 맥락을 압축·축적해 다음 대화에 되먹임하는 구조**다.

> "AI가 유저 데이터로 똑똑해진다"는 의미의 학습이 아니라, "이 유저와 있었던 일을 요약해 다음번에 다시 불러오는" 컨텍스트 누적 방식이다.

이 구분을 명확히 하지 않으면 "실시간으로 모델을 파인튜닝한다"는 식으로 오해될 수 있다.

---

## 2. 6단계 파이프라인

| 단계 | 처리 내용 |
|---|---|
| ① 원시 로그 수집 | 유저-NPC 대화 전체를 기록하되, 템플릿 응답인지 실제 LLM 응답인지 태그를 남긴다. |
| ② 요약 추출 | 원문을 영구 저장하지 않고, 세션 종료 시점에 결정·감정·선호 등 핵심만 짧은 요약으로 압축해 저장 비용과 토큰 비용을 통제한다. |
| ③ 관계별 프로필 축적 | 이 요약이 "유저 × NPC" 조합별로 누적된다 — 함장 일지 시스템과 같은 결의 데이터 구조. |
| ④ 다음 대화에 되먹임 | 재대화 시 전체 원문이 아닌 압축 요약만 프롬프트에 포함시켜, NPC가 "기억하는 것처럼" 보이되 비용은 통제된다. |
| ⑤ 게임 상태로 승격 | 정책 선택(Governor System)처럼 일부 결정은 단순 대화 기억을 넘어 실제 게임 상태(행성 정책, 비콘 위치)에 영구 반영된다. |
| ⑥ 온디바이스 우선 저장 | 아크코어의 기존 원칙(연산은 스마트폰, 최종 결과만 Firebase)과 동일하게, 관계 데이터도 기기 우선 저장 후 최종 상태만 동기화한다. |

---

## 3. 구현 가능성 평가

| 단계 | 구현 방법 | 난이도 |
|---|---|---|
| ① 원시 로그 수집 | 메시지마다 템플릿/LLM 여부를 태그로 남겨 로컬 저장(Zustand + AsyncStorage). 기존 스택 그대로 사용 가능 | 낮음 |
| ② 요약 추출 | 세션 종료 시 Claude API를 한 번 더 호출해 "결정·감정·선호"만 뽑아 요약 생성 | 낮음 (단, 4.1절 비용 주의) |
| ③ 관계별 프로필 축적 | (유저×NPC) 키로 작은 텍스트 블록을 로컬 저장, 최종본만 Firebase 동기화 — 기존 "최종 결과물만 동기화" 원칙과 정확히 일치 | 낮음 |
| ④ 다음 대화에 되먹임 | 저장된 요약을 시스템 프롬프트 앞부분에 삽입 — 표준적인 프롬프트 엔지니어링 기법 | 낮음 |
| ⑤ 게임 상태로 승격 | 대화에서 나온 결정을 실제 게임 상태(정책, 비콘 위치)로 반영 | 중간~높음 (4.2절 참고) |
| ⑥ 온디바이스 우선 저장 | 기존 아크코어 저장 구조 그대로 재사용 | 낮음 |

**결론**: 6단계 모두 현재 기술 스택(React Native, Zustand, Firebase, Claude API)으로 구현 가능하며, 아크코어의 기존 설계 원칙과 정합성이 높다.

## 4. 실무 주의사항

### 4.1 비용 — 요약 추출은 새로운 비용 항목이다

기존 하이브리드 엔진 비용 모델과 3개월 매출 시뮬레이션은 "유저가 말 걸 때만 LLM 호출"을 전제로 했다. ②번(요약 추출)은 유저가 대화를 많이 할수록 늘어나는 **별도의 LLM 호출**이므로, 기존 비용 모델에 이 항목이 반영되어야 정확해진다.

### 4.2 안정성 — 게임 상태 승격은 구조화 추출로 처리한다

자유 대화에서 "유저가 정책을 선택했다"를 정규식/키워드로 추출하면 오작동 위험이 크다(엉뚱한 대화를 정책 결정으로 오인식 등). **Claude API의 tool use(함수 호출)** 기능을 사용해, LLM이 "이 대화에서 유저가 실제로 무엇을 결정했는지"를 구조화된 JSON으로 직접 반환하도록 설계하는 것을 권장한다. 실제 게임 상태를 변경하는 지점이라 안정성이 특히 중요하다.

## 5. 목적과의 연결

| 개발 목적 | 이 파이프라인이 기여하는 방식 |
|---|---|
| **최고 성능 NPC AI 데이터 확보** | 실제 유저 대화 로그(①·②)가 쌓이면서, 어떤 대화 패턴이 몰입감을 주는지·어떤 요청이 템플릿으로 안 커버되는지에 대한 실증 데이터가 축적된다. 이는 향후 템플릿 라이브러리 개선, 프롬프트 튜닝, 파인튜닝 데이터셋 후보로 쓰일 수 있는 자산이다. |
| **성능 유지** | AI 토탈코어의 자기 최적화 원칙(audit:arc-self-optimize)과 동일한 결로, 쌓이는 대화 데이터 품질을 지속 모니터링해 반복 오작동이나 부적절한 응답을 조기에 감지·개선한다. |
| **시장 수요 확보** | NPC 대화 품질 자체가 유저 재접속·과금을 유도하는 핵심 차별점이 된다(앞선 "왜 유저에게 필요한가" 문서 참고). 파이프라인이 검증되면 아크파이어 전용을 넘어 다른 게임사에도 라이선싱 가능한 기술 자산이 된다(투자자 제안서 3절 "확장성" 카드와 연결). |

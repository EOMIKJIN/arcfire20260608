# 0. 최상위 원칙 — 문맥과 전달력 🔴

```text
대표님 지시 (2026-09-24):
「NPC 이야기 전개 시 가장 중요한 대사 처리에서 문맥과 전달력이
 이 시스템 기반에서 작성되어야 한다. 이 점이 가장 중요하다.」
→ 향후 대사 생성 · 스토리 전개 · 문맥 개선의 «주요사항»으로 기록한다.
```

## 0-1. 왜 우리 시스템에서 유독 중요한가

일반적인 대화 시스템은 **두 화자가 문맥을 나눠 세운다.**

```text
[플레이어] 그 배가 어디로 갔지?      ← 무엇을 묻는지 «플레이어가» 세운다
[NPC]      캠프 쪽이다.              ← NPC는 답만 하면 된다
```

**우리는 침묵형 주인공이라 플레이어 문장이 존재하지 않는다.** 그래서 NPC 한 사람이 네 가지를 **동시에** 져야 한다.

| NPC 한 사람이 지는 짐 | 일반 시스템에서는 |
|---|---|
| ① **무엇이 오갔는지 세우기** | 플레이어 대사가 했다 |
| ② 정보 전달 | NPC |
| ③ 감정·태도 | NPC |
| ④ 다음 행동 지시 | NPC |

그런데 **표시 공간은 3줄 × 21자로 고정**이다(§3). **짐은 두 배인데 그릇은 그대로**다.

> **이것이 침묵형 주인공의 진짜 비용이다.** 플레이어 목소리를 지우는 대신, **NPC 대사가 혼자 문맥을 세우고 동시에 전달해야 한다.** 여기서 실패하면 시스템 자체가 무너진다.

## 0-2. 우리가 겪은 결함은 전부 이 하나의 실패였다

96페이지를 고치게 만든 결함들을 다시 보면 **전부 같은 뿌리**다 — **플레이어 대사가 있는 것처럼 쓴 NPC 대사**.

| 실패 대사 | 무엇이 없었나 | 일반 시스템이었다면 |
|---|---|---|
| 「**그** 손버릇」 | 「그」가 가리킬 대상 | 플레이어가 앞서 손버릇을 물었을 것 |
| 「**문**은 여기서 닫는다」 | 무슨 문인지 | 플레이어 문장이 화제를 세웠을 것 |
| 「**칸**이 아니면 끊는다」 | 무엇의 칸, 무엇을 끊나 | 질문이 목적어를 공급했을 것 |
| 「아르카디아 살인사건 때 **그 손**이다」 | 「손=범인」이라는 전제 | 대화 흐름이 깔았을 것 |

**즉 결함 6종(§4-1)은 6개가 아니라 1개다.** 「NPC 대사가 혼자 서지 못했다」.

## 0-3. 단 하나의 통과 기준

> ## **이 대사는 앞 문장 없이 혼자 읽혀도 뜻이 서는가?**

플레이어는 **매 페이지를 맨손으로 맞는다.** 자기가 한 말이 없으므로 기댈 것이 없다. 이 질문 하나를 통과 못 하면 **다른 모든 규칙을 지켜도 전달되지 않는다.**

## 0-4. 3줄 안에서 문맥과 전달력을 동시에 세우는 6가지 기술

| # | 기술 | 실패 → 성공 |
|---|---|---|
| 1 | **첫 줄에 장면을 세운다** — 누가·어디서·무슨 상황 | 「요새 적색정보다」 → **「요새 정보반의 오렌이다」** |
| 2 | **지시대명사 대신 명사** — 「그/이/저」는 앞에 대상이 있을 때만 | 「그 손이다」 → **「아르카디아 살인범과 동일인이다」** |
| 3 | **은유는 구체를 깐 뒤에만** — 실물로 3번 쌓고 마지막에 한 번 | 「문」 3회를 **「관문」**(실물)로 → 마지막에만 **「돌아올 곳이 있다면 그게 고향이다」** |
| 4 | **한 페이지 한 정보** — 3줄에 정보 3개를 넣으면 0개가 남는다 | 정보는 페이지로 나누고, 한 페이지는 한 가지만 매듭짓는다 |
| 5 | **플레이어가 한 일을 되비춘다** — 그래야 자기 행동을 확인받는다 | 「채널을 바꿨다」(계기 없음) → **「켓의 대조 결과를 들이댈 줄은 몰랐군」** |
| 6 | **마지막 줄에 다음 행동** — 페이지가 닫힐 때 갈 곳을 안다 | 「증언은 요새에서 닫겠다」 → **「대조가 끝나면 요새에서 보자」** |

## 0-5. 전달력 자가 측정

작성 후 소리 내어 읽고 확인한다.

1. **한 번에 읽히는가** — 되돌아가 다시 읽어야 하면 실패
2. **모르는 말이 있는가** — 사전에 없는 절단 용어는 즉시 교체(§4-2)
3. **읽고 나서 무엇을 해야 할지 아는가** — 모르면 ④가 빠진 것
4. **이 인물이 말한 것 같은가** — 아니면 목소리 축이 무너진 것(§4-3)

> **이 4문을 통과하지 못한 대사는 CSV에 넣지 않는다.**

## 1. 결론 — 우리는 이미 침묵형 주인공이다

참조 규격을 현재 구현과 전수 대조한 결과, **핵심 3원칙은 이미 충족**돼 있고 **갭은 선택지 확장 하나**다.

| 참조 규격 항목 | 우리 구현 | 근거 |
|---|---|---|
| 플레이어 음성·서술 대사 배제 | ✅ **이미 충족** | 대사 101p 전수 확인 — **플레이어 대사 0건**. `[닉네임]`은 NPC가 호명할 때만 등장 |
| NPC 주도 서사 | ✅ **이미 충족** | 모든 정보·감정·지시가 NPC 발화로만 전달 |
| 선택을 상태값으로 변환 | ✅ **이미 충족** | `IngameDialogCompletionAction` — `accept_quest_mission` · `accept_main_story_mission` · `record_orbit_comm{outcome}` |
| 2지 선택 (수락/거절) | ✅ **이미 충족** | `ingameDialogTypes.ts:78-85` · `acceptLabel '[ 수락 ]'` · `questAcceptLabel '[ 의뢰 수락 ]'` · `onCancel` |
| **2~4개 선택지 배열** | ❌ **미구현** | 3지 이상 선택지 자료구조 없음. CSV에도 칸 없음 |
| **선택별 NPC 리액션 분기** | ❌ **미구현** | `story_scene_pages`는 `pageIndex` 선형 진행만 |
| INQUIRY / STAT_CHECK 유형 | ❌ **미구현** | — |
| 런타임 LLM 대사 생성 | ⛔ **HOLD** | ZERO_BILL(종량 $0 강제). 참조 규격 §3은 **런타임이 아니라 집필 기준으로** 적용한다 |

**따라서 이 문서의 역할은 두 가지다.**
1. **지금 당장** — 참조 규격의 §1·§2·§3을 **집필 규칙**으로 전환해 적용한다(§4·§5). 코드 변경 0.
2. **향후** — 선택지 확장이 필요해지면 §6의 단계안을 따른다. **지금 착수 대상이 아니다.**

## 2. 우리 구조에 맞춘 원칙 재정의

참조 규격을 그대로 쓰지 않고, 우리 2게이트 구조(`CONVERSATION_TWO_GATE_DESIGN.md`)에 맞춰 옮긴다.

### 2-1. 화자 격리 — 절대 규칙

> **플레이어는 말하지 않는다.** 대사·독백·생각 어느 것도 쓰지 않는다.

플레이어의 의도는 **선택 버튼**과 **NPC의 반응**으로만 드러난다. 이것은 취향이 아니라 **하드 계약**이다 — 한 번이라도 플레이어 대사를 쓰면 플레이어가 자신을 투영할 공간이 사라진다.

**금지 예시**

```text
✗ [ 나 ] 그 배가 어디로 갔는지 아나?
✗ (플레이어는 잠시 망설였다.)
✗ [ 한로 ] "어디로 갔냐고? 좋은 질문이군."   ← 플레이어 말을 복창
```

**올바른 예시** — NPC가 질문을 받았다는 사실만 반응으로 드러낸다

```text
✓ [ 한로 ] 그 배 말인가.
           도킹장에서 얼굴 하나를 봤네.
           목격자라면 그 얼굴이겠지.
```

### 2-2. NPC는 선택지를 복창하지 않는다

플레이어가 고른 문장을 되읊으면 **선택의 무게가 사라지고 분량만 늘어난다.** NPC는 **선택의 의도**에 반응한다.

| 플레이어 선택(의도) | ✗ 복창 | ✓ 의도 반응 |
|---|---|---|
| `[ 수락 ]` | "수락하겠다고 했군." | "그럼 됐다. 관문은 열어 두겠다." |
| `[ 취소 ]` | "거절이군." | "…그렇다면 다른 손을 찾겠다." |

### 2-3. 게이트 구조 준수

| 게이트 | 우리 구현 | 대사 작성 시 |
|---|---|---|
| 1. 통신 | `presentIngameDialogScene` / `presentAdHocIngameDialog` | **여기에 퀘스트 대사를 쓴다.** `[ 다음 ]` 또는 `[ 수락 ]`/`[ 취소 ]` |
| 2. 메신저 | `presentArcCoreBackchannel` (NL) | **퀘스트 대사를 쓰지 않는다.** NL 입 전용 |

- 게이트 1과 2를 **동시에 스택하지 않는다**
- NPC 씬은 메신저를 호출하지 않는다

## 3. 표시 규격 — 어길 수 없는 물리 제약

`.cursor/rules/arcfire-ingame-dialog-ui-default.mdc` + `narrativeDialogLayout.ts` 실측.

| 항목 | 값 |
|---|---|
| 본문 최대 줄 수 | **3줄** (`\n` 2개) |
| 줄당 한글 | **21자** (320dp 기준 상한 = `floor((W−28)/12.7)−1`) |
| 권장 집필 목표 | **20자** — 상한에 붙이면 여유가 0이다 |
| 초과 시 | 엔진이 자동 분할 → `[ 다음 ]` 페이지가 **의도치 않게 늘어난다** |
| `\n\n` 빈 줄 | 표시되지 않음 |
| 레이아웃 상수 | **변경 금지** |

> 집필 후 **각 줄을 세어 본다.** 21자를 넘으면 문장을 쪼개는 것이 아니라 **줄여 쓴다.**

## 4. 집필 체크리스트 — 새 대사를 쓸 때마다

### 4-1. 🔴 절대 금지 6가지 (실제 사고 사례 기반)

`QUEST_DIALOGUE_REWRITE_PROPOSAL.md`에서 96페이지를 고치게 만든 결함들이다. **처음부터 피한다.**

| # | 금지 | 사고 사례 |
|---|---|---|
| 1 | **뜻이 깨진 전문용어** | 「호출**부**」 — 「호출부호」의 절단형. 사전에 없는 말이 된다 |
| 2 | **받는 말이 없는 은유** | 「문은 여기서 닫는다」 — 무슨 문인지 앞에 없다 |
| 3 | **주어·목적어 과잉 생략** | 「칸이 아니면 끊는다」 — 무엇의 칸, 무엇을 끊나 |
| 4 | **허공을 가리키는 지시대명사** | 「**그** 손버릇」 — 직전에 손버릇이 나온 적 없다 |
| 5 | **고유명사 충돌** | 「나는 **칼**이 아니다」 → 등장인물 **칼 릿지**로 읽힘 · 「아우라 **바다**」 → 바(bar)가 바다(海)로 |
| 6 | **번역투 어순** | 「값은 이미 받은 것이다」 · 「얼굴은 켓이 연다」 |

**자가 점검 3문**
1. 이 문장의 **지시대명사가 가리킬 대상이 앞 문장에 있는가?**
2. 이 **은유를 받쳐 줄 구체 정보를 먼저 깔았는가?**
3. 이 **고유명사가 다른 등장인물·일반명사와 겹치지 않는가?**

### 4-2. 용어 표준 (전 대사 공통)

| 쓰지 않음 | 쓴다 |
|---|---|
| 호출부 | **식별 신호** |
| 대역 | **주파수** |
| 선석 | **정박 자리** |
| 칸(장부) | **줄 / 자리** |
| 일련 | **일련번호** |
| 왜곡권 | **왜곡 구역** |
| 초계 | **순찰** |
| 깃발(소속) | **세력 / 소속** |
| 꼬리 | **흔적** |
| 로그 | **기록** |
| 바 | **술집** |
| 숫자(전사자) | **전사자 수** |

> 새 전문용어를 도입할 때는 **첫 등장에서 뜻을 문맥으로 풀어 준다.** 못 풀면 쓰지 않는다.

### 4-3. 캐릭터 목소리 — 성별은 어미가 아니라 4축으로

**여성이라고 `~요`를 붙이지 않는다.** 여성 지휘관이 부하에게 존댓말을 쓰게 되어 계급이 무너지고 번역체가 된다.

| 축 | 남성 | 여성 |
|---|---|---|
| **종결** | 체언·명사 종결 — 「기습이다」 | 동사 종결 — 「이어진다」 |
| **문장 연결** | 단문 나열, 접속 생략 | 연결어미 — `~고`·`~는데`·`~더군` |
| **정보 순서** | 결론 먼저 | 근거·관찰 먼저, 판단 뒤 |
| **지시 방식** | 명령형 — 「확인해라」 | 계급 없으면 부탁형 — 「확인해 줘」 |

**계급·역할이 성별보다 우선한다.** 명령·전투 장면은 남녀 모두 단정체를 유지한다.

추가 축: **나이**(노년 = `~네`·`~일세`·`~하게`) · **군/민간**(군 = 짧고 정확 / 민간 = 길고 부연).

> **같은 인물이 장면마다 다르게 말하지 않는지** 확인한다 — 한로 크레인이 대기 대사는 노년체, 퀘스트 대사는 단정체였던 사고가 있었다.

### 4-4. 성별·대명사

- 신규 NPC는 **이름 + 스토리 배역**으로 성별을 먼저 정한다(`npc_ai_captains.csv`에 성별 컬럼 없음 — 로스터 정본은 `QUEST_DIALOGUE_REWRITE_PROPOSAL.md` §13-1)
- **3인칭 대명사를 쓰지 않는 편이 안전하다.** 「그를 찾아가」가 여성 NPC를 가리켜 틀린 사고가 있었다 → **이름을 다시 부르거나 대명사를 뺀다**(국어에서 자연스럽다)

### 4-5. 서사 연결

- **복선은 반드시 호명한다.** 「같은 수법이다」로는 전달되지 않는다 → 「**아르카디아 살인사건** 때 그 수법이다」
- **전환에는 계기를 준다.** 위장하던 인물이 아무 계기 없이 자백하지 않게, 플레이어가 한 일을 대사에 넣는다 — 「**켓의 대조 결과**를 들이댈 줄은 몰랐군」
- **반전을 미리 소진하지 않는다.** 앞 씬에서 「신원은 확인됐다」고 해놓고 뒤에서 이름을 최초 공개하면 반전이 죽는다
- **메타 용어 금지.** 등장인물이 「튜토리얼」·「본편」·「챕터2」를 말하지 않는다

## 5. 씬 작성 템플릿

### 5-1. 퀘스트 수락 씬 (게이트 1 · 수락/취소)

```text
p0  [ 의뢰인 ]  상황 제시 — 무슨 일이 있는가
                (3줄, 각 20자 이내)
p1  [ 의뢰인 ]  플레이어에게 무엇을 원하는가 + 왜 당신인가
p2  [ 의뢰인 ]  첫 행선지·첫 행동을 명확히
                → [ 의뢰 수락 ] / [ 취소 ]
```

**수락 시** `completionActions: [{ type: 'accept_quest_mission', ... }]`
**취소 시** `onCancel` — 메신저를 열지 않는다

### 5-2. 목표 진행 씬 (talk_npc 대상)

```text
p0  [ NPC ]  플레이어가 온 이유에 대한 «반응» (복창 금지)
             + 가진 정보 제시
p1  [ NPC ]  다음 행동 지시 또는 한계 선언
             («내가 아는 건 여기까지다»)
             → [ 다음 ] / [ 확인 ]
```

### 5-3. 목표문 (`mission_objectives.csv` · `description`)

- **명령형으로 통일** — 「~하라」. 명사형(「~도착」) 금지
- **직책만 쓰지 않는다** — 「광산총감독에게」 ✗ → 「광산 총감독 **니카 스톤**에게」 ✓ (허브에서 누구를 찾을지 알 수 없다)
- **서로 구분되게** — 「하루를 정리하라」/「하루를 닫아라」처럼 거의 같으면 플레이어가 구분 못 한다

### 5-4. 미션 설명문 (`missions.csv` · `description`)

- 대사보다 **정보량이 많아야 한다**(퀘스트 로그용)
- **한 문장 1정보**로 푼다
- 「플레이어」라는 개발 용어 대신 **「당신」**

## 6. 선택지 확장 — 향후 단계안 (지금 착수 아님)

참조 규격의 「2~4개 선택지 + 분기」를 도입하려면 아래 순서가 필요하다. **대표님 지시가 있을 때만 착수한다.**

| 단계 | 내용 | 비고 |
|---|---|---|
| 1 | **2지(수락/취소)를 이야기에 적극 활용** | **코드 변경 0 · 지금 가능.** 현재 수락/취소는 퀘스트 수락에만 쓰인다. 중간 씬에서도 태도 분기로 쓸 수 있다 |
| 2 | CSV에 선택지 스키마 추가 (`choiceId`·`label`·`nextSceneId`) | Table-First 유지. 김팀장 설계 |
| 3 | INQUIRY형(정보 질문 후 본류 복귀) 도입 | 분기 폭발 없이 정보량만 늘리는 안전한 유형 — **2번째로 권장** |
| 4 | STAT_CHECK형 | 능력치·평판 연동 필요. 가장 나중 |
| ⛔ | **런타임 LLM 대사 생성** | **ZERO_BILL 위반.** `ARC_CORE_CHAT_ZERO_BILL_REDESIGN.md` HOLD 해제 전까지 금지 |

> **분기 폭발 경고**: 선택지 N개 × 깊이 D면 대사량이 N^D로 는다. INQUIRY형(본류 복귀)을 기본으로 삼고, **진짜 분기는 퀘스트당 1~2회**로 제한한다.

## 7. 사용 규칙 (명시)

0. **§0(문맥과 전달력)이 이 문서의 최상위 원칙이다.** 대사 생성·스토리 전개·문맥 개선 **모든 작업의 첫 기준**이며, 다른 절과 충돌하면 §0이 이긴다. 작성 전 **§0-3 통과 기준 1문**, 작성 후 **§0-5 자가 측정 4문**을 반드시 거친다.
1. **새 퀘스트·대사를 작성하기 전에 이 문서를 연다.** §4 체크리스트와 §5 템플릿이 작성 기준이다.
2. 작성 후 **§4-1 자가 점검 3문**과 **§3 줄 수·글자 수**를 반드시 확인한다.
3. 이 문서와 개별 퀘스트 설계안이 충돌하면 **이 문서가 우선**한다. 예외가 필요하면 handoff에 사유를 남긴다.
4. 결함 사례의 상세 근거는 `QUEST_DIALOGUE_REWRITE_PROPOSAL.md`(사례집), 게이트 구조는 `CONVERSATION_TWO_GATE_DESIGN.md`(정본)를 본다.
5. 신규 용어·신규 NPC 성별을 확정하면 **§4-2 표와 로스터에 추가**한다. 가이드는 살아 있는 문서다.

# 굿케이스 — 「고치려다 더 엉킨 버그」 진단 패턴

```text
status=REFERENCE (재사용 패턴 · 특정 기능 문서 아님)
date=2026-09-24
승인=대표님 「완벽하다. 굿케이스로 저장」
원사례=은하 지도 Voronoi 변경 성계 영역 폭주
사례문서=docs/GALAXY_VORONOI_FRONTIER_TERRITORY_FIX_DESIGN.md
```

> **이 문서는 특정 버그의 해설이 아니라 다음에 쓸 절차다.** 「A를 고치면 B가 깨지고, B를 고치면 A가 돌아온다」는 상황에서 순서대로 적용한다.

---

## 0. 이 패턴을 꺼낼 신호

- 같은 자리를 여러 번 고쳤는데 **매번 다른 곳이 깨진다**
- 「특수 케이스만 예외 처리」를 반복하다 **분기가 계속 늘어난다**
- 고친 사람이 **무엇이 무엇을 고쳤는지 설명하지 못한다**

원사례의 신고 문구가 정확히 이랬다 — *「이 문제를 고치느라 기존 국경선이 망가지고 코드도 엉키게 되었다. 잘라내는 시도를 하다가 전체 다른 성계까지 엉키게 되었다. 가상 성계를 추가하는 것도 효과가 없었다.」*

---

## 1. 신고된 증상을 원인으로 믿지 않는다

**신고 증상 1개 → 실제 원인 3개**였고, 그중 **2개는 신고 증상과 무관한 기존 결함**이었다.

| | 원인 | 신고 증상과의 관계 |
|---|---|---|
| A | Voronoi에 영향 반경 개념이 없음 | 직접 원인 |
| **B** | **채움과 국경선이 서로 다른 클립 사각형으로 각자 Voronoi 생성** | **무관 · 기존 결함** |
| C | 클립 사각형이 사이트 bbox 기반이라 전역으로 흔들림 | 무관 · 기존 결함 |

**원인 B가 「고치려다 망가지는」 현상의 정체였다.** 채움을 고치면 국경선이 어긋나고, 국경선을 고치면 채움이 어긋난다. 신고 증상만 쫓았다면 영원히 못 찾는다.

> **행동**: 증상 주변 코드를 읽을 때 **「이건 이번 증상과 상관없는데 이상하다」 싶은 것을 따로 적어 둔다.** 그게 진범인 경우가 많다.

---

## 2. 「고치면 다른 게 깨진다」 = 공유돼야 할 기반이 불일치한다

가장 재사용도가 높은 패턴이다.

```text
소비자1 ─┐
         ├─ 같은 입력으로 «각자» 파생물을 만든다  ← 여기가 어긋나면
소비자2 ─┘                                        한쪽을 고칠 때마다 반대쪽이 깨진다
```

원사례에서:

| 소비자 | 클립 사각형 | 위치 |
|---|---|---|
| 영역 채움 | 사이트 bbox + 48 | `buildGalaxyTerritoryVoronoi.ts:323` |
| 국경선 | mapBounds 원본 | `buildGalaxyBlueRedVoronoiBorders.ts:77` |

호출부는 **같은 값을 넘기는데 한쪽만 내부에서 축소**했다. 내부 데이터는 결과가 같아 **오래 안 드러났고**, 변경 조건이 생기자 터졌다.

> **행동**: 같은 원본에서 파생물을 만드는 지점이 2곳 이상이면 **파생 규칙이 완전히 동일한지 먼저 대조**한다. 다르면 그것부터 통일하고 **단독으로 검증**한다.

---

## 3. 국소 문제에 전역 도구를 쓰지 않는다

| 도구 | 성격 | 결과 |
|---|---|---|
| 클립 사각형 축소 | **전역** | 하나 잡으려다 **반대편 성계까지 잘림** |
| 반경 클램프 (셀 ∩ 원) | **국소** | 해당 셀만 깎이고 **이등분선은 불변 → 다른 셀 0픽셀 변화** |

> **판별 질문**: **「이 수정이 문제와 무관한 대상을 건드리는가?」** 건드린다면 도구의 범위가 문제의 범위보다 크다. 더 좁은 도구를 찾는다.

---

## 4. 새 개체를 파이프라인에 넣기 전, 소비자를 전수 센다

「가상 성계 추가」가 실패한 이유는 아이디어가 나빠서가 아니라 **진입 지점이 넷이었기 때문**이다.

```text
가상 사이트 → ① bbox 계산  ② 국경선 edgeOwners  ③ 라벨 UnionFind  ④ 채움 fills
```

넷 전부에서 빼내야 하고, 제외 조건이 하나 늘 때마다 분기가 는다. **코드가 엉킨 경로가 정확히 이것이었다.**

> **행동**: 배열/집합에 항목을 추가하기 전에 **그 배열을 읽는 곳을 전부 센다.** 3곳을 넘으면 «추가» 대신 «후처리»를 검토한다.

---

## 5. 답은 기존 설계에 이미 들어 있을 수 있다

「빈 우주 쪽에도 국경선을 그어야 하나?」 — 새 규칙을 발명할 필요가 없었다. **기존 색 체계가 답을 갖고 있었다.**

| 색 | 의미 |
|---|---|
| 노랑 | blue ↔ red |
| 파랑 | blue ↔ neutral |
| 빨강 | red ↔ neutral |
| 녹색 | independent |

**모든 색이 「양쪽에 누가 있는가」를 인코딩한다.** 반대편이 빈 우주면 **칠할 색이 정의되지 않는다** → 긋지 않는 것이 유일하게 일관된 선택.

> **행동**: 새 규칙을 만들기 전에 **기존 규칙이 무엇을 전제하고 있는지** 읽는다. 전제를 드러내면 답이 따라 나온다. **발명보다 발견이 안전하다.**

---

## 6. 규칙 개수를 줄일 수 있으면 아직 덜 정리된 것

1차 정리에서 상태를 **3개**로 봤다.

```text
① 맞닿음  ② 빈 우주와 접함  ③ 떨어져 있음
```

다시 보니 **규칙 2개**로 전부 설명됐고 ③은 ②의 자동 귀결이었다.

```text
1. 이등분선이고 양쪽 원 안  →  실선
2. 그 외 모든 변            →  페이드
```

**예외 0개.** 플레이어도 한 문장으로 이해한다 — 「선은 두 나라가 맞닿은 곳에만 있다」.

> **행동**: 규칙을 다 쓴 뒤 **「이 중 다른 것에서 따라 나오는 게 있나?」**를 한 번 더 묻는다. 특수 케이스가 남아 있으면 모델이 아직 안 맞은 것이다.

---

## 7. 진단은 read-only로 — 남의 작업 트리를 건드리지 않는다

동료가 복구 중일 때도 진단은 가능하다. 원사례에서 실제로 쓴 방법:

| 목적 | 안전한 수단 |
|---|---|
| `git add` 실패 재현 | **`git add -n`(dry-run)** — 인덱스 무변경으로 exit 1 재현 |
| 무시 규칙 확인 | `git check-ignore -v` |
| 과거 버전 대조 | `git show HEAD:<path>` — 체크아웃 없이 |
| 변경 규모 | `git diff --shortstat` |

> **행동**: 「재현하려면 고쳐 봐야 한다」는 대개 사실이 아니다. **dry-run·조회 명령으로 먼저 시도**한다.

---

## 8. 원인이 여럿이면 단계를 합치지 않는다

원인 3개를 한 번에 고치지 않았다.

```text
0단계  되돌리기 (반쯤 진행된 시도 위에 덧칠 금지)
1단계  원인 B만 수정 → 실기 확인   ← 여기서 끊는다
2단계  반경 클램프
3단계  외곽 변 연출 분리
```

> **행동**: 합치면 **「무엇이 무엇을 고쳤는지」 판정이 불가능**해지고, 실패 시 다시 엉킨다. **1단계 후 반드시 한 번 멈춘다.**

---

## 9. 되돌릴 지점을 먼저 확보한다

0단계가 가능했던 이유는 **직전에 커밋·푸시가 되어 있었기 때문**이다(`ddf2fa5`). 되돌릴 곳이 없으면 0단계 자체가 불가능하고, 엉킨 상태 위에서 고칠 수밖에 없다.

> **행동**: 대규모 수정·복구 **착수 직전에 커밋 1회.** 이것이 굿케이스의 전제 조건이었다.

---

## 10. 요약 — 다음에 쓸 순서

1. 신고 증상 주변에서 **「무관한데 이상한 것」**을 따로 적는다
2. 같은 원본에서 파생물을 만드는 곳이 2곳 이상이면 **파생 규칙 대조**
3. 수정 도구가 **문제보다 범위가 넓지 않은지** 확인
4. 개체 추가 전 **소비자 전수 카운트** (3곳 초과 → 후처리로 전환)
5. 새 규칙 발명 전 **기존 규칙의 전제**를 읽는다
6. 규칙을 쓴 뒤 **개수를 줄여 본다**
7. 재현은 **dry-run·조회 명령**으로
8. 원인별로 **단계를 쪼개고 사이에 실기 확인**
9. 착수 전 **커밋 1회**
